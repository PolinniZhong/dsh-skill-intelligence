## 1. 产品命题与结论

### 1.1 产品问题

用户的问题不是「Skill 太少」，而是 **Agent 的 Skill 层对普通人不可见**。用户在 DSH 中安装越来越多 Skill，能看到最终回答，却难以判断：

- 本次对话究竟加载过哪些 Skill，各自加载了几次；
- 每个 Skill 自己声明能做什么、以什么方式被调用（模型自动调用 `model`，还是用户输入 `/name`）；
- 当前会话加载的这个 Skill，定义现在能不能读到、读到的这一版和当时那一版是不是同一版；
- 这个 Skill 的定义原文到底写了什么、来自哪个仓库、是不是本机可解析的来源；
- 本机 / 当前工作区与 Agent Preset 下究竟可发现哪些 Skill，不记得准确名称时如何不依赖输入 `/` 找到它；
- 定义是英文、用户不是英文母语时，能不能先读一版中文阅读版再决定要不要用。

现有的 Skill 管理、动态路由、使用统计与通用轨迹产品分别回答「有哪些」「该挂载哪些」「累计用了多少次」「Agent 做了什么」。本产品要补的是那条**本地可复核的阅读链路**：本会话的实际加载证据 + 逐字定义原文 + 可核对的定义指纹，既不拿运行时事件反推声明步骤，也不替用户判断 Skill 有没有执行、有没有用。

### 1.2 产品承诺

> **让每一次实际 Skill 加载留下可核对的本地证据，并让用户看懂每个 Skill 声明了什么、这次留下了哪些相关观察。**

这句话里没有「理解」「学会」「掌握」——本产品**不替用户形成知识**，只把该看见的东西摆到该在的位置。

### 1.3 产品定位

DSH Skill Intelligence 不负责安装、启停、更新、市场或自动路由 Skill。它以 Skill 为一级对象只读呈现：**这次对话用了哪些 Skill**、**本机 / 当前作用域能发现哪些 Skill**；点进任意一张卡，看这个 Skill 的摘要、定义事实、仓库来源与逐字 `SKILL.md` 原文。

**V1.0 起定位扩展到四个动作：理解 / 修改 / 验证 / 实验 Skill**（V1.0 已随 `1.0.0` 发布，见 §5.13）。这里的「**实验**」有严格边界：它是**可重复的本地记录与对照**——同一份任务 Prompt 可以反复运行，每次运行的条件与可观察事实并排摆出来；**不是**插件替你调用模型、替你跑任务，也不是替你判定结果。

它记录加载证据，不判断因果：

- `skill(name)` 成功，只能写「已加载」；
- Agent 是否遵循方法、方法是否促成结果，由用户确认；
- 没有观测到事件，只能写「未观测」或「覆盖未知」；
- Skill 声明的步骤不等于 Agent 已执行的步骤；声明内容只能来自定义正文，运行时证据只能标注，不能增删改序；
- 不评分、不给百分比、不做排名，也不使用「未观测到执行」这类词。

### 1.4 目标用户与核心 JTBD

**主要用户**：在 DSH 中频繁使用多个 Skill、希望看懂 Agent 工作方法的普通用户。
**次要用户**：需要排查 Skill 调用、回顾方法使用情况的 Skill 作者与 Agent 工作流设计者。

1. 一次对话结束后，我想一次点击就看清它实际加载过哪些 Skill、各自几次、以什么方式被调用，再点进同一个详情页读定义事实与逐字原文，以便确认 Agent 到底用了什么能力包，而不是只能看最终回答。
2. 当我准备开始一项工作、或不记得 Skill 的准确名称时，我希望不输入 `/` 就能按名称或描述搜索本机 / 当前作用域可发现的 Skill——这份目录必须独立于我这次对话加载了什么。
3. 当 `SKILL.md` 是英文而我不是英文母语时，我想在不修改原文、不污染对话的前提下读到一版中文阅读版，以便判断这个 Skill 是否适用于我手头的工作。

## 2. 目标、指标与非目标

### 2.1 目标

1. **知道这次对话用了什么**：可靠记录已验证标准 `skill(name)` 事件的请求、成功、失败与恢复态，并关联 Session、Turn、Step，把技术事件转成普通用户可读的加载事实。
2. **读懂这个 Skill 声明了什么**：逐字呈现 `SKILL.md` 原文，并用确定性解析给出它的组成结构、声明流程、渐进披露、本次运行逻辑与步骤证据。
3. **看清本机有什么**：不依赖 `/`、不依赖本次对话是否加载过，给出本机 / 当前作用域的只读发现目录。
4. **看懂外文定义**：英文定义可以在不改原文、不污染对话的前提下读一版中文阅读版，并且这版译文是可复用、可核对的本地资产。
5. **能复用它**：可以从一个现有 Skill 复制出一个独立的新 Skill，源一个字节都不动。
6. **绝不干扰 DSH**：插件关闭、异常、未覆盖或本地写失败时，DSH 原生 Session、Agent 与 Skill Consumer 行为不变。

### 2.2 成功指标

| 指标 | 门槛 | 验证阶段 |
|---|---:|---|
| 持久化敏感正文数量 | 0 条 | Spike + Beta |
| 「已加载」被写成「已遵循 / 已成功」 | 0 条 | 文案测试 + Beta |
| 「未观测」被写成「未使用」 | 0 条 | 覆盖矩阵测试 |
| 插件关闭后 DSH 原生流程回归 | 0 个阻断回归 | 技术 Spike |
| 试点用户 60 秒内回答「用了什么、以什么方式加载」 | 不低于 80% | 内部 Beta |
| 中文阅读版出现在收据 / 备份 / `localStorage` / `sessionStorage` / 会话日志 / 用户对话中 | 0 条 | Translation 测试 |
| 坏输入导致整个 Tab 卸载或空白 | 0 次 | 详情页错误态测试 |
| 列表首屏读取 `SKILL.md` 全文的次数 | 0 次 | 投影测试 |
| 用户在 5 秒内回答「本机可发现多少个 Skill」 | 不低于 80% | 可用性测试 |
| 用户在 10 秒内按名称或描述找到目标 Skill | 不低于 80% | 可用性测试 |
| 「Skill 声明」与「本次加载事实」被混为一谈 | 0 个关键误解 | 可用性测试 |

前四项是发布硬门槛；产品价值假设不达标时优先调整信息结构，不扩大功能。

### 2.3 非目标

- 不做 Skill 市场、安装器、更新器、批量启停或来源同步；
- 不做动态路由、自动挂载、远程发现或质量评分；已安装 Skill 只是只读发现目录，不是弱化版 Skill Hub；
- 不做模型、工具、Skill 排名与趋势 Dashboard，也不做遵循率、百分比或评分；
- 不从 Agent 最终文本猜测 Skill 已使用；不自动判断 Skill 对结果有因果贡献；
- 不自动执行 Skill 脚本、不修改用户项目、不下载远程资源；复刻只新建目录、只写副本（见 `FR-UI-061`）；
- 不重新绘制运行流程 / 运行图谱，不提供上下文检查器或声明-运行时对照面板；
- 不恢复跨会话学习工作台、学习笔记、验证结果、输出引用或迭代清单；
- 不自动生成、修改、覆盖、安装、执行、提交或发布 Skill；
- **除「中文阅读版」外不做任何模型调用**：翻译只把**当前 Skill 的定义正文**发给用户自己配置的 DSH 模型一次，不发送会话 Prompt、Tool 内容、Cookie 或 credential；
- 不把用户数据上传给开发者或第三方；不实现遥测、云同步、收据上传或远程分析；
- 不修改、不耦合 `dsh-visual-acceptance`：两者独立安装、独立关闭、独立维护，运行时没有调用关系，也没有共享 Store。
- **不产出任何聚合指标**（V1.0 起继续成立，见 §5.13 `FR-EVAL-012`）：断言通过率、n 次通过次数、平均分、稳定性百分比、方差与标准差、Skill Score、排名与趋势图**一律不许出现**——断言只逐条列，对照只并排摆事实；
- **不做 benchmark 排名**，不做跨 Skill / 跨模型横向榜，也**不拿两个不同任务的运行结果互相对比**（§5.13 `FR-EVAL-013`）。
- **V0.8 明确不做**（见 §5.7）：Skill Marketplace、GitHub Skill 搜索、自动筛选或 AI 推荐「优秀 Skill」、Skill 评分 / 排名 / 质量分、Skill IDE、Markdown 编辑器、自动改写或自动优化 Skill、A/B 行为测试、Baseline / With-Skill 实验、自动回归测试、自动运行 Skill 或 `scripts/`、自动发送 `/name`、自动执行当前会话；也不新增学习工作台 / 笔记 / 复习队列、不新增 Marketplace 页面、不新增 Skill 资产后台、不新增第二套 Skill Registry / 调用引擎 / Agent Runtime、不为本版本新增强制 Agent Mode。**质量评价与行为归因整体留给 V0.9+**——V0.8 只为「演进」建立可靠的事实基础（血缘 + 确定性差异）。

## 3. 核心对象与状态语义

### 3.1 五层业务事实

| 层级 | 用户表达 | 成立条件 | 不能推出 |
|---|---|---|---|
| L1 | 已发现 | 当前 `ctx.skills.snapshot()` 观察中存在 Skill 摘要 | 当前 Agent 可调用 |
| L2 | 已可用 | 有可验证证据表明该 Skill 对当前 Consumer 可见且可调用 | Agent 一定会加载 |
| L3 | 已加载 | `skill(name)` 的调用与成功结果已可靠配对 | Agent 完整遵循了方法 |
| L3b | 定义可读 | 该 Skill 的 `SKILL.md` 当前能被读到，并算出当前 `sha256` 指纹 | 定义内容与本次加载时的那一版相同 |

L4「有输出关联」与 L5「人工确认有用」已随输出引用与学习工作台从产品中删除，不再有任何产生路径。

任何层级都不得由更低证据直接跳级。若当前 Consumer、事件字段或观测范围无法确认，则显示 `coverage-unknown`，**不能显示「未使用」**。「定义可读」只说明现在读得到，不说明它和历史版本一致——那要靠 `FR-UI-019` / `FR-UI-037` 的指纹比对，且只有一侧有指纹时必须落到「无法比对」。

### 3.2 加载状态

| 状态 | 含义 |
|---|---|
| `requested` | 已收到 Skill 工具调用，尚未收到可配对结果 |
| `loaded` | 调用与成功结果已配对 |
| `failed` | 调用与失败结果已配对 |
| `outcome-unknown` | DSH 恢复后无法确认工具是否已经执行 |
| `not-started` | DSH 恢复后确认工具尚未开始 |
| `unresolved` | 仅用于不完整或异常记录，不作为正常 DSH 生命周期的目标状态 |
| `coverage-unknown` | 当前 Consumer 或事件形态不在已验证适配范围内 |

加载证据状态图：`Observing → Requested`（标准 Skill `tool/call`）；`Observing → CoverageUnknown`（事件形态未验证）；`Requested → Loaded / Failed / OutcomeUnknown / NotStarted / Unresolved`；`Loaded / Failed / OutcomeUnknown / NotStarted / Unresolved / CoverageUnknown` 均为终态。这些状态由保留的 `src/core/trace-reducer.mjs` 维护。

### 3.3 三个对象域不可互相推导

- **`Declared`**：来自 `SKILL.md` 定义正文，逐字读取，不经过任何模型、Embedding 或检索；
- **`Observed`**：来自 DSH 运行时事件，只保留关联与分类元数据，不读参数与结果内容；
- **`Inferred`**：尽量不做。

方向不可逆：`SKILL.md → Definition → Framework → 声明流程 → 运行证据只能标注它`。

### 3.4 人工有效性边界

产品**不提供**「有用 / 没帮助 / 不确定」入口——当前没有开发者接收、统计或用户侧复用闭环，展示该入口会制造错误预期。旧收据中的 `humanAssessment` 仅作本地 Schema 兼容，不进入界面、指标或持久化 Gate。任何「这个 Skill 有用 / 正确 / 被遵循了」的表达都不允许出现。

## 4. 信息架构与页面职责

### 4.1 页面清单

**一级页面恰好两个，二级页面恰好一个——就这些。**

| 页面 | 内部键 | 数据来源 | 回答的问题 |
|---|---|---|---|
| 本次 Skill | `current`（默认） | 本地收据的 load evidence（`trace-reducer.mjs` 是这一层的唯一 reducer） | 这次对话加载了哪些 Skill |
| 已安装 Skill | `installed` | 只调 `GET /skill-trace/catalog`，由 `buildInstalledView` 从 registry snapshot 投影 | 本机 / 当前作用域能发现什么 |
| Skill 详情 | — | 两个一级列表的共同二级页 | 这个 Skill 声明了什么、这次观察到了什么 |

两个一级页面是**同级但语义不同**的两个页面，不是同一个列表的两种筛选，**数据源不得互相借用**。

**没有 `Advanced` 组。** 运行流程 / 运行图谱 / Skill 收据 / 上下文检查器 / 声明流程面板 / 跨会话学习工作台已在信息架构收敛中整体删除，**不得以折叠区、次级标签或「更多」菜单的形式复活**；15 条已删宿主路由与 `buildRuntimeGraph` / `computeRuntimeLayout` / `buildCatalogView` 由契约守卫反向钉住。

**评测不新增页面**（V1.0，已随 `1.0.0` 发布，见 §5.13）：Skill Evaluation 只在**详情页内**作为「本次修改对比 → 实例验收」之后的一段出现，**不新建「测试中心」或「评测仪表盘」**，不新增一级 / 二级页面，不新增导航项。

### 4.2 详情页的四层顺序

主内容区自上而下**固定为**：

1. **Skill 框架**（结构 + 声明流程 + 渐进披露）——由 `src/core/skill-framework.mjs` 从定义正文确定性解析；
2. **本次运行逻辑**——由 `src/core/skill-runtime-logic.mjs` 从当前收据推出，五段：目录 → 载入 → 指令 → 运行能力 → 证据；
3. **步骤证据**——把 `detail.flow.steps[].evidence` 里已算好的依据显示出来；
4. **`SKILL.md`**——原文与中文阅读版。

**这个顺序是需求，不是排版**，由守卫按字面匹配。四层加上左栏（Skill 摘要 / Definition 事实 / Repository）共同构成唯一详情页。

### 4.3 返回路径与设置入口

- 返回按钮文案**必须由来源 state 派生**（「返回 Skill 列表（本次 Skill）」/「返回 Skill 列表（已安装 Skill）」），绝不硬编码——写死返回目标会把从另一个列表进入的用户送到从未去过的页面。
- 设置只保留**默认一级页面偏好**（`PREFERENCES_VERSION = 3`，取值恰好 `current` / `installed`）以及当前 Observer 覆盖与数据保存位置的脱敏表达。备份 / 导出 / 恢复 / 草稿暂存入口已删除。

## 5. 功能需求（`FR-*`）

> **id 是承重结构**：其他文档引用这些编号，因此每条需求都保留其原始 id 与原始标题，不重新编号、不复用已作废的编号。已撤销的编号（`FR-CON-*`、`FR-LRN-*`、`FR-DATA-*` 及 `FR-UI-005/006/012/013/015/016/017/020/021/022/028/029/030/031/039/042/053`、`FR-SKL-012/013/014/016`、`FR-SCOPE-001`–`012` 的多数）**ID 保留、内容作废，不得复用**。

### 5.1 事件观测与证据（`FR-OBS-*`）

- **`FR-OBS-001`**：系统必须只把已验证 Skill Consumer 的工具调用识别为 Skill 加载请求。
- **`FR-OBS-002`**：系统必须按 Session、调用标识、Turn、Step 配对 `tool/call` 与 `tool/result`。
- **`FR-OBS-003`**：系统必须区分 `requested`、`loaded`、`failed`、`outcome-unknown`、`not-started`、异常 `unresolved` 与 `coverage-unknown`。
- **`FR-OBS-004`**：系统不得从 Assistant 文本、Skill 名称出现或目录可见性推断「已加载」。
- **`FR-OBS-005`**：系统必须记录观测器类型与覆盖状态，使「未观测」可解释。
- **`FR-OBS-006`**：插件停止、异常或被禁用时不得阻断 Session、Agent 或 Skill Consumer。
- **`FR-OBS-007`**：单条事件没有 Consumer 注册来源时必须显示「身份不可区分」；产品级覆盖可列出已验证 Consumer，但不得把它归因给某次调用。

### 5.2 会话收据（`FR-REC-*`）

收据作为**证据对象**保留，但没有独立页面；其加载证据由「本次 Skill」一级页面消费。

- **`FR-REC-001`**：系统必须按会话生成一张可重启读取的本地收据。
- **`FR-REC-002`**：收据必须保留实际加载的 Skill、发生步骤、成功/失败与证据引用；这套事实的**展示位置**是「本次 Skill」一级页面的卡片（名称、描述、调用方式、加载次数、定义可读状态），收据本身不作为页面出现。
- **`FR-REC-003`**：失败、结果未知、未开始和异常未配对事件在**数据层**必须与成功加载保持可区分（由 `trace-reducer.mjs` 保证）；「本次 Skill」只呈现加载事实，**不得把缺证据写成「未加载」**。
- **`FR-REC-005`**：不提供「有用 / 没帮助 / 不确定」的人工反馈入口——当前没有远程回传、开发者接收或后续闭环。旧收据中的 `humanAssessment` 仅作 Schema 兼容，不参与展示与持久化判断。
- **`FR-REC-006`**：用户删除收据或全部本地数据前，系统必须显示删除范围并二次确认。
- **`FR-REC-007`**：同名 Skill 在一张收据中只能占一个 Skill 条目，其调用次数、成功次数、失败次数由 reducer 聚合；不提供逐事件展开入口。
- **`FR-REC-008`**：一个 Skill 包含成功与失败等不同事件时，Skill 级状态必须显示为「状态混合」，不得用单次成功覆盖失败证据。
- **`FR-REC-009`**：成功结果包含标准 Skill 指令标签时，收据只保存 SHA-256 指纹和有界结构，不保存正文；指纹只用于内容相等比较，**不称为签名或防篡改证明**。

### 5.3 已安装 Skill 与 Skill 详情（`FR-SKL-*`）

- **`FR-SKL-001`**：一级页面「已安装 Skill」（内部键 `installed`）只读展示当前作用域可发现的 Skill，**只调用 `GET /skill-trace/catalog`，由 `buildInstalledView` 从 registry snapshot 投影**；不提供启停、安装、更新或同步。
- **`FR-SKL-002`**：系统必须区分 Registry 已发现与当前 Consumer 已可用；证据不足时显示未知。
- **`FR-SKL-003`**：详情左栏必须显示 Skill 自述（名称、描述、调用方式）、`provider · source kind`、当前 `SKILL.md` 的 sha256 指纹与本次会话加载次数。
- **`FR-SKL-004`**：完整 Skill 正文只能按需读取和临时展示，默认不得复制到收据存储。
- **`FR-SKL-005`**：入口名称使用「已安装 Skill」，语义限定为**本机 / 当前作用域可发现**；保留「不得把发现结果写成全局库存」的约束，不使用「当前可发现 X 个」作为入口文案。
- **`FR-SKL-006`**：列表概要优先读取 Skill 自带 `name / description / provider / safe source / version`；说明不足时显示「该 Skill 没有提供足够清晰的用途说明」，**不得调用模型补写**。
- **`FR-SKL-007`**：用户可按 Skill 名称和描述在**客户端**本地搜索；不得以任何形式保留「暂未观测 = 从未使用」的暗示。
- **`FR-SKL-008`**：列表项只分开展示**发现状态**与**定义可读状态**；收据状态与个人学习状态不进入该列表——那是「本次 Skill」与收据数据各自回答的问题。
- **`FR-SKL-009`**：Skill 详情的组织顺序固定为：左栏 Skill 摘要 / Definition 事实 / Repository，右栏逐字 `SKILL.md` + Outline。
- **`FR-SKL-010`**：未留下真实加载事件的 Skill 在「已安装 Skill」中只呈现发现与定义事实；**该列表刻意不读收据，因此不得显示「暂未观测到实际加载」**，也不得生成虚构流程、使用次数或结论。
- **`FR-SKL-011`**：列表与详情不提供安装、卸载、启停、更新、市场、来源同步、新建 Skill、使用排行或质量评分入口。
- **`FR-SKL-015`**：当前目录必须从已挂载普通会话的 Agent Preset 作用域 Registry 读取；不得使用无法看到 Preset 内 Skill 的根级 Registry，也不得把只返回用户可调用项的 `/` 菜单 RPC 当成完整目录。

### 5.4 用户界面（`FR-UI-*`）

#### 5.4.1 第一屏与默认页

- **`FR-UI-001`**：默认入口先回答「这次用了哪些 Skill」；第一屏是本次 Skill 卡片，点一次进唯一详情页；用户不得被迫先理解 Turn / Step / Invocation / Scope / Edge 一类概念。
- **`FR-UI-007`**：默认一级页面只允许 `current` / `installed`，**没有 `Advanced`**。偏好以 `PREFERENCES_VERSION = 3` 写入；读取时任何无版本号的值，以及任何 v0.5 词汇（`skills` / `map` / `receipt` / `audit`），一律视为「从未表达偏好」并归一化为 `current`（判据：文件里没有字段能证明那个旧值是用户选的，而 `map` 已不是页面——尊重一个无法实现的旧选择本身就是错误行为）。
- **`FR-UI-040`**：进入产品不得先出现运行图谱，也不得先面对 `Session / Turns / Nodes` 一类计数；第一屏是本次 Skill。详情首屏范围内必须同时出现 Skill 名称与简介、Definition 事实与逐字 `SKILL.md` 原文。
- **`FR-UI-041`**：从进入到看懂一个 Skill 最多一次点击，禁止四层以上下钻。
- **`FR-UI-014`**：本次 Skill 卡片固定展示名称、描述、调用方式（`model` / `/name`）、本会话加载次数与定义可读状态。
- **`FR-UI-035`**：本次 Skill 列表只展示本次会话有真实加载证据的 Skill；不得把已安装目录当作「本次使用的 Skill」，反之亦然。
- **`FR-UI-018`**：会话头部可显示一枚轻量状态提示，但必须与本次 Skill 同源读取收据投影，不生成第二套分析。

#### 5.4.2 页面状态与空态

- **`FR-UI-002`**：界面必须为加载、空、错误、无可靠 Trace、覆盖未知提供各自独立的状态。
- **`FR-UI-010`**：加载中只显示一句进度提示；无 Trace 时只显示一句空态，不渲染卡片骨架、依赖、产出或推断结论。
- **`FR-UI-011`**：已确认标准事件覆盖且事件为空时显示「当前对话暂未加载任何 Skill」；覆盖未知时显示「暂时无法确认当前对话是否加载了 Skill」，**不得写成「未使用」**。
- **`FR-UI-025`**：「已安装 Skill」空态必须区分「作用域完整但无发现结果」「作用域覆盖未知」「搜索无匹配」三者。
- **`FR-UI-026`**：已安装 Skill 入口不依赖当前会话是否有 Trace，零 Skill 会话仍保留该入口。
- **`FR-UI-051`**：页面不得因坏输入卸载整个 Tab；任何缺失字段必须降级为可见错误状态（一句说明 + 可重试），不得整页崩溃或空白，也不得把缺失字段静默当空值渲染。

#### 5.4.3 事实字段与指纹

- **`FR-UI-004`**：每个事实字段必须自述其边界（例如指纹比对直接写「无法比对」），不依赖可展开的证据面板。
- **`FR-UI-019`**：Definition 事实卡必须显示文件 `SKILL.md`、**当前** sha256 指纹、本次会话加载次数、`provider · source kind`，以及「请求版本 vs 当前版本」的指纹比对；**只有一侧有 hash 时必须写「无法比对」**，不得温和降级成「文件已改变」。
- **`FR-UI-037`**：指纹比对必须保留 `Observed Definition Hash` / `Current Definition Hash` 与三态 `match` / `mismatch` / `unavailable`；界面结论只在三态之间选一个。禁止把 `unavailable` 写成 `mismatch`，也禁止写成「Skill 已失效」——哈希只证明版本变化，不证明好坏。（界面中文以代码为准：`match` → 「一致」，`mismatch` → 「文件已改变」，`unavailable` → 「无法比对」。）
- **`FR-UI-038`**：Repository 是详情标准信息卡；地址按三级解析：Skill frontmatter → 所在 git worktree 的 `origin` → 用户配置。禁止根据目录名、Skill 名或 npm 包名猜测 GitHub；猜不到显示「未解析」，不伪造、不留禁用态占位。**带凭据的 remote 与本机绝对路径整条拒绝展示。**
- **`FR-UI-036`**：Skill 运行记录以宿主给出的事件标识（`eventId` / `callId` / `turn-step`）为准，**不得伪造 `runId`** 或其它 DSH 没有的原生字段。

#### 5.4.4 页面集合与导航

- **`FR-UI-023`**：顶级导航恰好两个一级页面（`current` 默认 / `installed`），语义不同，`installed` 带客户端搜索框；不存在 `Advanced` 组。
- **`FR-UI-043`**：一级页面恰好两个（同 `FR-UI-023`，含「刻意不读收据」与客户端搜索框）。
- **`FR-UI-044`**：二级页面恰好一个（Skill 详情）；两个列表的任意卡片都进入同一个详情页；**返回按钮文案必须由来源 state 派生**，绝不硬编码。
- **`FR-UI-024`**：一级页面切换不得改变默认页面偏好、不得丢失当前 Skill；从详情返回必须回到进入它的那个列表。
- **`FR-UI-008`**：一级页面切换或从详情返回必须保留当前 Skill 与来源列表；页面切换不得改变任何业务状态。
- **`FR-UI-045`**：详情左栏固定三张卡：Skill 摘要卡、Definition 事实卡、Repository 卡。
- **`FR-UI-009`**：颜色不得作为唯一编码。
- **`FR-UI-003`**：界面直接使用「Skill」，新手解释可称「工作方式」，同时保留「Skill 是指令与资源包，不是人类专家」。

#### 5.4.5 语言

- **`FR-UI-027`**：界面语言跟随 DSH `zh` / `en` 设置；宿主运行中切换后当前 Tab、会话状态提示与插件自有文案原位刷新，未知 locale 回退英文。Skill 名称、声明、证据字段、工作区名与收据正文不翻译、不重写、不上传；`SKILL.md` 正文只在用户显式触发中文阅读版时翻译。

#### 5.4.6 声明与观测的边界

- **`FR-UI-032`**：Skill 是产品的一级对象，Tool / MCP / CLI / Subagent 不是（只能作为 Runtime Evidence 来源）；技能列表禁止显示 Tool 数 / Runtime 节点数 / Runtime Edge 数。
- **`FR-UI-033`**：声明内容只能来自 Skill 自己的定义文本，逐字渲染 `SKILL.md`，运行时证据不得改写、补写或反推定义；不得为此引入 LLM / Embedding / 向量库 / RAG / 自动摘要 / AI 分类——唯一例外是用户显式触发的中文阅读版。
- **`FR-UI-034`**：数据模型与界面必须区分 `Declared` / `Observed` / `Inferred`；禁止「某 Tool 距离某 Skill 最近 ⇒ 属于该 Skill」，也禁止「同一 Turn ⇒ 把该 Turn 全部运行时事件算成该 Skill 的」。
- **`FR-UI-052`**：UI 不得做 declared → runtime 推断：不得由运行时事件反推声明步骤，也不得把「已加载」渲染成「已执行」。方向不可逆：`Skill Definition → 阅读`，绝不是 `Runtime → Flow`。

#### 5.4.7 详情页四层

- **`FR-UI-054`**：详情必须在 `SKILL.md` **之前**渲染「Skill 框架」，由 `buildSkillFramework()` 从定义正文**确定性**解析（不得调用模型总结、不得由运行证据反推）。框架三个子模块：结构（小节归入八个角色，未归类的小节进「其它章节」而不是被丢弃；正文里没有的角色在 `coverage.absent` 里直说缺什么、不补齐）、声明流程、渐进披露。它回答「这个 Skill 由什么组成」，不是「它说自己分几步」。
- **`FR-UI-054a`**：**声明流程不等于 Skill 框架**——`detail.flow` 一个字不删，但只能在框架内作为「声明流程 · Declared Workflow」子模块出现。`extractDeclaredFlow()` 抽到的是 `SKILL.md` 里某一小节的有序列表；把它当成能力包的整体形状，就会把 342 行 / 11 小节 / 39 个外部资源的 Skill 说明成四步。
- **`FR-UI-054b`**：**声明资源不等于已读取资源**——渐进披露只显示 `SKILL.md` 写到的引用；没有来源证据证明某个文件被读过之前，`resources.loaded` 必须为空，界面不得出现「已读取 references/tokens.md」，也不得假装追踪到资源调用。同一路径先后出现多次只产出一条记录（`alsoDeclaredAt` 记下其余行号）。
- **`FR-UI-054c`**：另起一层「本次运行逻辑」，只陈述本次会话能观察到的事实；五段固定为 `目录 → 载入 → 指令 → 运行能力 → 证据`，由 `buildSkillRuntimeLogic()` 从当前收据推出。没有可关联运行事件时五段只能取最保守那一档，**不得写「没有运行」**；阶段之间没有因果顺序且必须在界面上说明；**这不是运行图**，不得画任何跨阶段或 Skill → Tool 的边。
- **`FR-UI-054d`**：`detail.flow.steps[].evidence` 必须真正显示出来——每个声明步骤给出后端已算好的依据（`relationship` / `runtimeEvidence` / `observedNodeIds` / `evidenceIds` / `matchedCapabilities` / `modelIntent` / `matchCount`），并常驻一句说明「『暂无足够证据』表示本次会话没有观察到可以对应的运行证据，**不代表这一步没有执行**」。
- **`FR-UI-054e`**：**四层的顺序是需求，不是排版**——详情页主内容区自上而下必须是 框架 → 本次运行逻辑 → 步骤证据 → `SKILL.md`。
- **`FR-UI-055`**：框架里的每一步只能被标注、不能被构造；运行时证据只允许给已存在的声明步骤附加状态，不得新增 / 删除 / 重命名 / 重排任何一步，也不得由运行证据反推框架。实现上 `SkillFramework` 不得读取 `runs` / `invocations` / `observedNodeIds`。
- **`FR-UI-056`**：框架的状态词只陈述观察、不陈述执行。五档固定为「有相关运行证据 / 部分相关证据 / 仅有模型意图 / 暂无足够证据 / 无法判断」，与 `ALIGNMENT_RELATIONSHIPS` 一一对应；「已执行 / 未执行 / 已完成 / 未完成 / 执行成功 / 执行失败 / 已运行 / 未运行」八个词不得出现在界面任何位置；**没有证据不等于没有执行**；未知关系一律兜底为「无法判断」而不是「暂无足够证据」。
- **`FR-UI-057`**：框架标题下必须有免责句，逐字为「流程来自 SKILL.md 的声明；运行证据仅用于标注当前会话中的相关观察，不代表 Agent 内部推理过程。」不可改写、不可省略、不可只在 tooltip 里。点击某一步走文档已有锚点机制定位并高亮对应章节，不跳页、不打开运行图、不新增页面。合成小节的锚点是 `null`，渲染成**不可点的行**——「一个点了不动的按钮比不可点的元素更糟」。

#### 5.4.8 文档面板与表格

- **`FR-UI-046`**：右栏必须逐字渲染 `SKILL.md`（只读）并提供 `原文 / 中文阅读版` 段控；Outline 从**当前显示版本**的文档标题确定性抽取（切中文阅读版跟随中文阅读版，切回原文跟随原文，不得混用两版标题）。第三方 Markdown 视为不可信：不使用 `dangerouslySetInnerHTML`，fence 内文本原样保留且 fence 内 `#` 不当标题，inline code 保持，仅 http(s) 成为链接，`javascript:` 之类退化为文本，不执行文档中的代码或脚本。
- **`FR-UI-058`**：GFM 表格必须渲染成真表格，且原文与中文阅读版共用同一个渲染器；表头行 + 分隔行同时成立才算一张表（setext 的 `---` 不是分隔行）；单元格保留行内代码、链接与 `\|` 转义；表格不得吞掉相邻段落 / 标题 / 代码围栏；渲染器只允许一个调用点；不得为此引入 Markdown 库或布局引擎（`mermaid` / `marked` / `markdown-it` / `remark` / `rehype` / `reactflow` / `@xyflow/react` / `elkjs` / `d3`）。翻译侧同步校验表格形状（行数、列数、每行格数与分隔结构变化即判 `table` 失败并重试），但掩码占位符被破坏仍必须报 `placeholder`——报成表格会让用户去改一张没坏的表。

#### 5.4.9 中文阅读版

- **`FR-UI-047`**：中文阅读版只读：永不写回 `SKILL.md`、永不追加到用户对话、永不进入收据 / 备份 / `localStorage` / `sessionStorage`，也永不包含工具参数、工具结果或对话正文。翻译结果绑定 `sourceSha256`；定义在翻译期间变化必须按 `definition-changed` 失效并提示「Skill 内容已变化，请重新翻译」。（归档 PRD 曾说译文「只进内存」——**这一条已被 v0.7 的 `FR-UI-060` 取代**，以代码为准。）
- **`FR-UI-048`**：翻译必须保留结构：fence、URL、文件路径、inline code 与 frontmatter 逐字保留，只翻译散文；必须有 inspection 步骤比对源文与译文的 fence 数、标题层级、inline code、URL 与路径并报告违规；不得改命令 / 参数名 / 代码 / JSON / YAML / XML 结构，不得增删段落或改标题层级，不得添加额外解释性正文。
- **`FR-UI-049`**：翻译调用用户自己配置的 DSH 模型**一次**（`ctx.llm`），因此 UI 必须明说当前 Skill 的定义文本会发送到该模型 provider、除此之外不出本机；不得把完整 Session Prompt / Tool 内容 / Cookie / credential 作为翻译上下文，也不得向用户对话追加「请翻译……」一类消息。
- **`FR-UI-050`**：翻译失败时段控**回到「原文」（显示什么就是选中什么）**，但错误必须保持可见并提供重试入口，禁止静默失败。
- **`FR-UI-060`**：中文阅读版是**本机资产**——落盘 `<dataRoot>/translations/<sha256(key)>.json`（`0700` / `0600` + 原子 rename），键是 `skillName + sourceSha256 + targetLanguage`，**不含 `sessionId`**，因为它是资产而不是这次会话的产物，也不含工具参数 / 工具结果 / 对话正文。`sourceSha256` 变了，旧译文不得作为当前译文显示（回原文、允许重译），旧文件可留着供回退。「✓ 中文阅读版已保存」只能由写入真实发生后的 `saved` 布尔驱动——**发起请求不等于保存成功**；没写成必须说清并提示需要重译。译文永不写回 `SKILL.md`、不进收据、不进会话日志、不上传、不同步。

#### 5.4.10 复刻 Skill

- **`FR-UI-061`**：复刻 Skill 只能**新建目录**且必须回读验证后才允许宣称成功：
  - `POST /skill-trace/clone` 由宿主重新读取源 Skill 并重算 `sourceSha256`（不信任前端先前读到的值），不一致即 `409`；
  - 目标名必须满足 DSH 的 Skill 名语法（小写 kebab-case），同名一律拒绝并提示改名，**不得自动改名或编号**；
  - 写入用**不带 `recursive`** 的 `mkdir`（EEXIST 即冲突），**没有「先删再写」这条路**；半途失败要删掉刚建的目录；
  - 副本 frontmatter 的 `name:` 必须改写成目标名（DSH 认 frontmatter，不认目录名）；
  - 完成后必须回读副本校验 + 观察目录刷新；观察不到就写「目录刷新状态待确认」并说明重启后可见，不得声称已刷新；
  - 不得修改或覆盖源 Skill，不得执行 Skill 里的 `scripts/`、不跑 bash / Python、不触发 Agent，响应里不得出现本地绝对路径；
  - `sourceSha256` 不匹配 / 目标已存在 / 定义读不到 / 整包不可确认各有独立错误码与**人话说明**（`limitations` 是代码，界面必须翻译成句子，不得直接显示裸错误码）。

#### 5.4.11 界面收口（顶栏、间距、列表平行）

- **`FR-UI-062`**：顶栏只说必须说的话、不占不必占的高度：
  - 高度固定 **48px**，既不绘制自己的底色，也不绘制自己的分隔线；
  - 读法固定为「导航 → 这一页的状态 →（右侧）搜索 → 刷新」；
  - 搜索框属于已安装列表，只在已安装列表出现（详情页收起，目录读不到时也不出现），宽度 `220px`，窄屏先让位到 `140px`；搜索图标位于框内右端且不得抢占点击；
  - 刷新按钮保留但只留图标、不画底板；
  - **状态行只在有话要说时出现**——已安装列表一切正常时不显示状态行，也不显示孤立状态点；但失败与不确定的四句必须逐字保留：「正在读取当前环境…」「已安装 Skill 读取失败 · 宿主可能仍在运行旧版本」「当前目录无法确认 · 只显示已确认的部分」「目录可能不完整 · 已发现 N 个 Skill」。「一切正常」是唯一可以静默的情况，因为那时没有信息可加；
  - 分段控件的容器与选中项都不画背景框，选中态只靠 `--st-brand` 字色与 `font-weight:600` 高亮。
- **`FR-UI-063`**：卡片一律「上面是内容、下面是元信息」，元信息钉在卡片左下角：
  - 两个列表的元信息行（已安装列表上是「加入本机 / 复刻自」两行事实，另有例外时的调用方式与非常规 provider）都必须用 `margin-top:auto` 钉在卡片底部，不得跟着描述长短上下浮动；元信息里**只说例外**（见 `FR-ORD-013`），理由与 §4 状态行「一切正常是唯一可以静默的情况」同源；
  - 正文列没有 `gap` 的那张卡必须同时给 `padding-top`（`auto` 外边距在没有多余空间时解析成 0）；
  - 列表与顶栏之间不得有第二条空白带（顶栏 `48px` 放 `30px` 控件，上下各余 `9px`，已安装列表顶部内边距就是 `10px`）；
  - 两个一级列表必须平行：`.st-page`（本次 Skill）与 `.st-installed`（已安装 Skill）的内边距必须逐字相同（`10px 24px 28px`）——守卫钉的是这个**相等关系**，只改一页就会红。

### 5.5 运行时范围与禁止词（`FR-SCOPE-*`）

`FR-SCOPE-*` 多数条目随运行图谱删除而作废，ID 保留、内容作废、不得复用。仍然有效的两条禁令：

- **不得出现 `not-observed` / `skipped` / `not-done` 一类词汇**——缺证据只能写「未观测 / 覆盖未知」；
- **全产品不得计算或呈现遵循率、百分比、评分或排名**（由 `ALIGNMENT_NO_SCORE_OK` 守着）。

另有两条原则保持有效（对象已消失）：不得由时间相邻推断归属；不得绘制因果关系。

### 5.6 数据需求（`FR-DATA-*`）

`FR-DATA-*` 随备份 / 恢复 / 导出 / 清空 / 输出引用链路全部作废，ID 保留不得复用。仍然成立的结论：**不得引入云端、上传、同步、账号或遥测**。数据要求见 §8。

### 5.7 血缘与差异（`FR-EVO-*`）

> **本节已随 `0.8.0` 发布（2026-10-02）。** 实现全部落地，真机验收已于 2026-10-02 通过（12 个检查点，走查清单：`01_重构方案/v0.8-真机验收清单.md`）；本节描述的就是**现行版为真的事实**——Phase 1 血缘（复刻成功时落盘，随 `GET /skill-trace/skill` 的详情响应回、**不另开路由**）、Phase 2 差异（`GET /skill-trace/diff`，这一版唯一新增的一条路由）、Phase 3 详情页「Skill 演进」卡与「Skill 差异」面板。

`FR-EVO-*` 回答的是「复刻之后」的那一段：**我的 Skill 从谁来、我改了什么、来源现在变了吗**。它不新增一级页面（全部落在既有的唯一详情页内部），不建立版本系统，不评价优劣，不调模型。

**血缘（Lineage）**

- **`FR-EVO-001`**：血缘只有一个数据源：Skill Intelligence 自己成功执行过的复刻。内容相似、名字相似、同属一个 GitHub 仓库、用户自己在 Finder / Terminal 里复制的文件、用户自己新建的 Skill ——**都不建立血缘**。血缘是**需要证据支持的事实**，不是猜出来的关系；推断血缘的优先级不是「Diff」「相似度」或「AI 判断」。
- **`FR-EVO-002`**：一条血缘记录的字段是**闭集**：`lineageId`、`sourceSkillName`、`sourceSourceSha256`、`targetSkillName`、`cloneMode`、`targetScope`、`createdAt`、`catalogObservation`（`observed` / `pending`），以及可选的 `sourceRepository`。**不得包含**：任何 Skill 正文或资源文件内容、会话标识、会话日志、Tool 参数或结果、Token / Cookie、未脱敏绝对路径。
- **`FR-EVO-003`**：`sourceRepository` 只允许记录**已被确认**的仓库来源（frontmatter、`git origin` 或用户配置）。**不许按 Skill 名或目录名拼 GitHub URL**，不许记录带凭据的 URL。
- **`FR-EVO-004`**：一个目标 Skill 只允许一条「直接来源」记录。之后用户对目标 Skill 的任何修改（`SKILL.md`、`references/`、`scripts/`）都**不产生新记录**——那些变化归 Diff。同一个目标名再次被复刻时**覆盖**该记录（当前目录的来历 = 最近一次由本插件执行的复刻）。血缘不是历史变更日志。
- **`FR-EVO-005`**：写入时机：只有在 `writeClone` 成功、`readBackClone` 通过回读校验、且源 Skill 复核过之后才允许写血缘。**回读失败 ⇒ 不写血缘**（那条路径本来就整体回滚并失败）。目录刷新**观察不到**不等于复刻失败，写 `catalogObservation: 'pending'`。
- **`FR-EVO-006`**：写血缘失败**不得回滚副本、不得改变复刻结果**：只在响应 `limitations` 里加 `lineage-not-recorded`。把「副本已经在磁盘上」说成「复刻失败」是撒谎。
- **`FR-EVO-007`**：血缘只落在**插件自己的数据目录** `<dataRoot>/lineage/`（目录 `0700`、文件 `0600`、原子写、一记录一文件）。**不写进 Skill 目录**（那会污染该 Skill 的 bundle，并被后续的完整复刻拷走）、**不写进收据**、**不写进会话日志**，不上传云端、不同步 GitHub。
- **`FR-EVO-008`**：血缘与收据里既有的 `lineage` 键（**会话父子血统**：`parentSessionId` / `delegationDepth`）**是两个无关对象**。不得互相读写、不得共用字段名；文档里提到时必须带限定语（「Skill 复刻血缘」/「会话血统」）。

**演进（Evolution）**

- **`FR-EVO-009`**：详情页左栏内的「Skill 演进」块回答三个问题：**我是谁 / 我从谁来 / 来源现在变了吗**。数据随既有的 `GET /skill-trace/skill` 的 `lineage` 字段一起来，**不新增路由**。它**不许**长成时间线大页面、版本列表或 Git UI。
- **`FR-EVO-010`**：措辞是闭集：只许「当前 Skill」「来源 Skill」「复刻来源指纹」「当前来源指纹」「来源内容未发生变化」「来源内容已发生变化」「无法读取来源」。**不许**「原始版本」「当前版本」「版本升级」「版本降级」「版本落后」「最新版本」「旧版本」「来源版本过期」——「过期」「落后」已经带判断。
- **`FR-EVO-011`**：不建立版本实体：没有 Skill 版本号、没有 `v1` / `v2`、不要求 Skill 有 `version:` 字段。内容身份只有 `sha256` + 复刻时间 + 血缘关系。

**差异（Diff）**

- **`FR-EVO-012`**：差异分三层，全部**确定性**、**无模型参与**：结构（复用 `src/core/skill-framework.mjs` 的确定性解析）、内容（按 Markdown 结构组织的行级差异）、资源（文件系统事实）。
- **`FR-EVO-013`**：比较基准始终是「当前目标 Skill」与「当前来源 Skill」两侧的实时事实。插件**不保存**复刻当时的正文快照（见 `FR-EVO-002`）。因此来源已经变化时，两侧的差异**可能来自来源一侧，而不是用户改的**——界面必须把这件事说出来。
- **`FR-EVO-014`**：差异是**事实陈述**，不是评价。词表闭集：只许「新增」「删除」「修改」「保持不变」「来源内容已变化」「当前 Skill」「来源 Skill」「无法比较」。**不许**「更优秀」「更差」「质量提升」「质量下降」「优化成功」「优化失败」「建议保留」「建议删除」「推荐采用」「应该使用」「最佳版本」「最佳 Skill」。
- **`FR-EVO-015`**：来源或目标**读不到**时诚实表达：「当前无法读取来源 Skill，无法完成差异比较。」并带 `role="alert"`。**不许**把「读不到」说成「没有变化」。
- **`FR-EVO-016`**：资源差异必须按**本次复刻模式**解释：`cloneMode === 'skill-md'` 时来源的其它资源本来就没被复制到本地，界面必须明说；**不许**把「本地没有」呈现成「被删掉了」。
- **`FR-EVO-017`**：差异面板**只读**：可以查看、理解、对照；**不许**编辑、AI 重写、一键合并、一键同步来源版本；不执行 Skill 脚本、不调用 Agent、不修改任何 Skill 文件。**源 Skill 永不修改。**
- **`FR-EVO-018`**：差异面板是**标准模态**：打开后焦点进入面板内第一个可操作控件、焦点被限制在面板内（焦点陷阱）、`Esc` 立即关闭、关闭后焦点回到打开它的那个「查看差异」按钮。关闭**不改变页面导航**（不返回列表、不触发浏览器后退）。错误态 `role="alert"`；新按钮与新 Tab 沿用项目既有的 `:focus-visible`（2px 品牌色外框 + 2px 偏移），**不得覆盖 `outline`**。
- **`FR-EVO-019`**：差异**不返回、不显示任何本地绝对路径**。范围只说「当前项目 Skill」/「用户级 Skill」。

**接口与分层**

- **`FR-EVO-020`**：路由闭集：宿主只新增**一条** `GET /skill-trace/diff`（**10 → 11 条**）。**不新增** `/lineage`、`/evolution`、`/source`、`/versions`；血缘与演进随既有的 `/skill-trace/skill` 返回。
- **`FR-EVO-021`**：血缘与差异是宿主侧领域逻辑。 客户端只做「请求宿主 API → 拿视图模型 → 渲染」，**不 `require` 任何新增的 core / storage 模块，也不自己实现一套差异算法**。
- **`FR-EVO-022`**：已知限制，必须如实登记：来源 Skill 的名字如果已被另一个 Skill 占用，插件**无法识别**「名字还是那个名字，但已经不是同一个 Skill 了」。V0.8 不深挖（那要先给来源建立身份，属 V0.9+），只在血缘里如实记录可确认的 `sourceRepository`，让用户自己看得见来源对不对。

> **两处按默认落笔、待确认**（用户冻结的 8 条回答的是相邻问题，见 `design.md` §24）：
> ① `FR-EVO-013` 后半句的显式声明——用户回答的「血缘只来自成功复刻」是 B1 的**前一半**；在没有正文快照的前提下，「基准只能是当前 vs 当前 + 明说可能来自来源一侧」是被 `FR-EVO-002` / `FR-EVO-011` 与「一个目标一条记录」共同逼出来的唯一自洽解。
> ② `FR-EVO-022`——用户回答的 B3 是**目标名冲突**（目录与扁平 `.md` 都算，这是 `0.7.1` 已有行为，本次只补测试与守卫）；「来源名被顶替」这一条既没被接受也没被否决，按**记为已知限制、不动代码**落笔。

### 5.9 Skill 验收（`FR-VAL-*`）

> **本节已随 `0.9.2` 发布（2026-10-03）。** 实现已落地、`npm test` 与 `npm run verify` 已全绿、真实渲染台截图已核对（见 §12.2 与 §12.3），并已通过真机验收。本节与 §5.7 的区别只在发布的批次：§5.7 讲的是 `0.8.0` 的演进卡与差异面板（同样已发布），本节讲的是 `0.9.2` 新加的验收卡——紧接着的 §5.10 与 §5.11 也随 `0.9.2` 一起发布。

`FR-VAL-*` 回答的是**当前**这个 Skill 符不符合规范：`通过` / `需要修正` / `无法判断`，以及每一条结论对应哪条规则。它**不回答**「改完以后行为有没有变好」——那要先有基线、行为差与回归，属 V1.0+（§2.3）。它也不修改任何文件、不注册 Skill、不调用模型。

- **`FR-VAL-001`**：验收**不是评分系统**。结论只有三态：`pass` / `needs-fix` / `unknown`（界面：**通过 / 需要修正 / 无法判断**）。**不许**出现分数、百分比、等级、权重、排行榜、「优秀」「最佳」「推荐度」。允许的谓语只有「符合 / 不符合 / 存在警告 / 无法判断」。
- **`FR-VAL-002`**：只有**违反 error 规则**才进入 `needs-fix`。**`warnings > 0` 永远不等于 `needs-fix`**；`info` 不推状态。读不到 `SKILL.md` 时结论是 `unknown`，**不是** `needs-fix`：读不到不是「有错误」。
- **`FR-VAL-003`**：规范是**共同规范层 + 平台 Profile**，不是一个大杂烩。Common Core 抽取开放规范（agentskills.io）、OpenAI、Anthropic、Microsoft 四家的共同基础；DSH / OpenAI / Anthropic / Microsoft 各自独立成 Profile。**不得因为多家都提到某件事就写成「各家标准完全一致」**，也不得把平台差异抹平。
- **`FR-VAL-004`**：平台差异必须能被观察到，且**同一件事在不同 Profile 可以有不同严重度**。已冻结的例子：`name` 必须与父目录同名，Microsoft 原文是 "Must" ⇒ `MS-DIR-001` 是 **error**；DSH 的装载实现只看 frontmatter 的 `name`、不比对目录名 ⇒ **DSH Profile 里不存在这条规则**（不是 warning，是不存在）。
- **`FR-VAL-005`**：每条规则有固定身份：`id`、`profile`、`severity`、`title`、`fact`、`source`。`severity` 只有 `error` / `warning` / `info` 三档，**不许**「严重性 9」「风险分」这类连续量。**同一个 `fact` 只允许出现在一条规则里**，Profile 之间靠「引用同一条规则」共享，避免同一件事被写两遍、改一处漏一处。
- **`FR-VAL-006`**：Profile 选择默认 **DSH + Common**。`common` 永远补上（它是共同规范层）；只选平台时会自动补 `common`；用户没选或选了空集合，等价于「还没选」⇒ 用产品默认，不静默降级成只验 Common。高级模式才逐平台勾选（OpenAI / Anthropic / Microsoft / 多平台）。不能识别的目标名要如实出现在结论的说明里，**不许静默丢弃**。
- **`FR-VAL-007`**：**行数只能是 warning。** 四家来源都把 `SKILL.md` 控制在 500 行写成建议（"Keep … under 500 lines"），**四家的装载阻断清单里都没有行数** ⇒ 把它写成 error 就是把建议伪装成硬规则。
- **`FR-VAL-008`**：**「这次没查」不许渲染成「通过」。** 判定不了的规则进 `skipped` 并带**理由**，界面必须逐条说出理由（如「拿不到这个 Skill 的目录清单，无法判断引用的文件在不在」「正文太长，这次只读了一部分」）。每条 Profile 行单独汇总自己的 `checked / total`：一个 Profile 一条都没判成时，它自己是 `unknown`，**不跟着整体躺赢**。
- **`FR-VAL-009`**：安全检查**只报告观测到的字面模式**（凭据、硬编码密钥、危险命令、可疑外传、绕过权限），给 `warning` / `error`，**不许**写成「这份 Skill 是恶意的」这种意图判断。匹配到的值**不得回显**到验收结果里——把真密钥抄进结论是二次泄漏。
- **`FR-VAL-010`**：资源类规则**只判定这个 Skill 自己的资源**。路径落在 `scripts/` / `references/` / `assets/` 之下才参与「文件是否存在 / 是否逃出 Skill 根目录 / 引用是否只深一层」的判定；正文里提到的其它路径（例如在讲宿主工程住在哪）**不判**——那是宿主事实，不是 Skill 的资源声明。
- **`FR-VAL-011`**：目录清单的完整性**必须由 `SKILL.md` 自证**：清单里没有 `SKILL.md` 自己时，一律 `skipped`，**不许**得出「引用的文件不存在」。清单不完整时，「文件不存在」是一句指控，而指控需要证据。
- **`FR-VAL-012`**：**验收本身不新增路由。** 验收结果作为 `GET /skill-trace/skill` 与 `GET /skill-trace/definition` 两条既有响应的**同级字段 `validation`** 返回，两条路由共用同一个宿主函数，避免同一次请求把 `SKILL.md` 读两遍。（v0.9.1 为修改流程新增的 `POST /skill-trace/modify` 属于 §5.10，不属于验收；`0.8.0` 发布时宿主恰好 11 条路由，`0.9.2` 发布时是 12 条。）
- **`FR-VAL-013`**：界面只在既有的唯一详情页里多一张卡，**排在「框架 / 本次运行逻辑 / 步骤证据 / `SKILL.md`」四层之上**（它回答的是这一版的主问题，且它本身只读声明层）。**不新增页面、不新增一级导航、不注册 Skill、不做 Markdown 编辑器 / 文件树 / Git 面板 / 版本选择器。**
- **`FR-VAL-014`**：每条结论**可追溯到 rule**：发现行给出 `rule id` + 规则标题 + 严重度 + 说明，未判定行给出 `rule id` + 标题 + 理由。**不许**出现「这份 Skill 很规范」这种无出处的结论。
- **`FR-VAL-015`**：文案沿用项目既有词表纪律：结论词只有「通过 / 需要修正 / 无法判断」，严重度只有「错误 / 警告 / 信息」；**不得**出现声称已经发生的词（`已执行` / `已完成` / `已加载` / `已读取` …）与评分词（`评分` / `分数` / `等级` / `优秀` / `最佳`）。
- **`FR-VAL-016`**：无障碍沿用既有合同：结论用 `role="status"`；「读不到这个 Skill」与「宿主还没换到这一版的代码」两句用 `role="alert"`，且**必须是两句不同的话**——前者是 Skill 的现状，后者是宿主的版本状态，混在一起会让用户去改错的东西。
- **`FR-VAL-017`**：验收**只读 `SKILL.md` 与目录清单**：现读现返、**不落盘**、不进收据、不进会话日志、不上传、不调用模型、**不执行 Skill 里的任何脚本**、不返回本地绝对路径。规则表是纯常量，判定是纯函数。
- **`FR-VAL-018`**：分层固定：**规则表（事实）→ 验收器（判定，纯函数）→ 宿主接缝（读事实）→ 客户端卡（展示）**。判定函数**不许**碰文件系统、不许调模型、不许访问会话对象；事实由宿主读好再传进来。
- **`FR-VAL-019`**：版本边界：本版**只做验收（Validate）**。「告诉 Agent 怎么改」（Modify）属 V0.9.1；行为验证属 V1.0+。**不因为下一步有价值就把它塞进这一版。**
- **`FR-VAL-020`**：已知限制必须如实登记：静态验收**不能**证明这份 Skill 的指令真的有效果；`description` 是否准确说明用途需要人来判断；目录名与目录清单只在能定位到 Skill 目录时可判（线上来源的 Skill 没有目录）；安全两条只报告字面模式，不代表意图。

### 5.10 Skill 修改（`FR-MOD-*`）

> **本节已随 `0.9.2` 发布（2026-10-03）**（与 §5.9 同一批）。实现已落地、`npm test` 与 `npm run verify` 已全绿，并已通过真机验收。

`FR-MOD-*` 回答的是**「我想让它怎么改」**：用户写一句意图、勾出修改范围与要按哪些规范验收，点 `[交给 Agent]` 之后由**当前会话**的 Agent 在 DSH 原生对话里改；插件负责说清「改之前是什么、改之后是什么、改了多少、有没有超出范围」，**它自己一行文件也不写**。

- **`FR-MOD-001`**：修改发生在**当前会话的对话里**，由当前 Agent 用 DSH 原生工具完成。插件**不建第二套 Agent Runtime、不建专属会话、不复制粘贴**：DSH 上「起调这个会话」就是拿到当前会话的 Agent 句柄、再向它发一条后续消息。
- **`FR-MOD-002`**：**用户点 `[交给 Agent]` 这个动作本身就是发送授权。** 插件随后用当前会话的 Agent 代发一条消息，消息的 `source.kind` 是 `skill-intelligence-modify`，因此在运行记录里能认出它来自本插件。
- **`FR-MOD-003`**：**只有用户给的那个范围是结构化的。** 「提出方案 → 用户确认 → 动手」这段过程留在 DSH 原生对话里（Agent 该问就问，走 DSH 自己的提问机制），本版**不自造 Proposal RPC、不解析 Agent 的 JSON 方案**。代发的消息里必须**明确写出这个要求**（「动手之前：先说明你打算怎么改……有拿不准的地方就用提问工具问用户，不要在猜的基础上改文件。」）—— 插件不代办这件事，但也不能不提：不提就等于 Agent 直接动手。
- **`FR-MOD-004`**：**「改之前」只活在宿主内存里**：不写磁盘、不进收据、不进会话日志、不上传，DSH 重启后不保留。默认 30 分钟后过期，最多同时记 32 份。
- **`FR-MOD-005`**：一次修改事务**只用于一次对比**，比完就释放（超过上限时丢最早的一份）。这是「本次修改对比」，**不是历史版本库**。
- **`FR-MOD-006`**：**快照没了就说实话。** 拿不到改前状态时输出「本次修改前状态不可用，暂时无法比较本次修改的内容。」并在界面上如实呈现；**不许**用当前状态假装改前状态。此时 V0.8 的「来源 Skill ↔ 当前 Skill」差异仍然可用。
- **`FR-MOD-007`**：范围语义：本版可勾选 `SKILL.md / Rules`、`SKILL.md / Workflow`、`SKILL.md / Description`、`references/`；**`scripts/` 与 `assets/` 看得见但锁死**（不授予、不可勾选）。范围名认不出来时**如实报出**，不静默接受；范围为空时是一句明确的「只讨论，不要改动任何文件」。
- **`FR-MOD-008`**：**超出范围的变化单独列。** 只授权了 Rules 却动了 Workflow，或动了没被点名的资源，必须在「超出修改范围」里逐条说明——不与已授权部分混在一起，也不因此隐瞒已授权部分的结论。范围外的改动可以让结论落到 `needs-fix`。
- **`FR-MOD-009`**：**来源 Skill 始终只读。** 用改前 / 改后的 `sha256` 判断来源有没有变，三态：`unknown` / `unchanged` / `changed`。变了只输出「来源 Skill 在本次修改期间发生变化。」——**没有直接证据时不写「Agent 修改了来源」**。
- **`FR-MOD-010`**：顺序固定：**写入 → 回读 → 验收 → 对比**。对比复用 §5.9 的同一套验收器与规则表，**不另建一套判据**；对比结论文案只有「有变化 / 没有变化 / 无法比较」。
- **`FR-MOD-011`**：界面是既有的唯一详情页里的一张卡，顺序为 **验收 → 本次修改对比 → 框架 → 本次运行逻辑 → 步骤证据 → `SKILL.md`**。**没有修改事务时整块不渲染**（常驻的空卡会被读成一种状态）。不新增页面、不新增一级导航。
- **`FR-MOD-012`**：**插件不替 Agent 宣布结果。** 它不轮询、不猜「Agent 改完了没有」，只在用户要求对比时读一次盘上的事实。界面不许出现「已执行 / 已完成 / 已加载 / 已读取」这类词（与 `FR-VAL-015` 同一套词表）。
- **`FR-MOD-013`**：**不由插件调模型来总结或评价这次修改。** 展示的是行数增减、小节增减、资源增删改、范围逐项状态这些可核对的字面事实，**不给分、不排名、不评好坏**。
- **`FR-MOD-014`**：状态必须各自说话：意图为空、当前会话没有活着的 Agent、Skill 读不到、宿主注册表没挂载，都要有各自的句子（不许出现裸错误码，也不许沉默）。
- **`FR-MOD-015`**：`POST /skill-trace/modify` 是宿主第二条「不是纯读」的路由（第一条是复刻），但它**不写任何文件**：只把改前状态记进内存、再请当前会话代发消息。要再加路由，必须同时改 `AGENTS.md` §6.12 与 `spec/SDD.md` §3。
- **`FR-MOD-016`**：已知限制如实登记：静态对比只证明文件变了，**不证明改得好、更不证明行为变好了**（那要基线、行为差与回归，属 V1.0+）；插件**挡不住** Agent 改范围外的文件，只能如实报告；`scripts/` 里的代码从头到尾**不执行**；改前快照丢了就没有对比。

### 5.11 已安装列表排序（`FR-ORD-*`）

> 本节随 **`0.9.2`** 一起发布（2026-10-03）。用户原话：「「已安装 Skill」中带 custom 都是我用复刻 Skill 复刻出来的，现在排序又在后面……就是想在第一排就看到我刚才复刻的，这样我方便我找……我得翻好几页看名称看得到。」——所以列表要回答的是「**哪个是刚来的**」，而不是「哪个字母更靠前」。

- **`FR-ORD-001`**：已安装列表按 Skill **出现在本机的时间**倒序，最近加入的排在第一行。规则名 `added-desc-then-name`（`src/core/installed-view.mjs` 导出的 `INSTALLED_ORDERING_RULE`），随 `GET /skill-trace/catalog` 的响应字段 `ordering.rule` 下发；客户端**只念规则**，不自己排序，也不把这句话写死在界面里——顺序只有一个决定者。
- **`FR-ORD-002`**：这个时间是 **Skill 目录的文件系统创建时间（birthtime）**，由宿主对候选根下的 `<skillName>` 目录 `stat` 得到。**不是** mtime / ctime，**也不是**文件级 birthtime —— 契约里的 `.md` 每被改写一次就可能变成新文件、birthtime 跳到改动那一刻（真机实测：`SKILL.md` 是 23:29，而同一天复刻出来的**目录**仍是 22:39）。「它什么时候来到这台机器」不得因为改了正文而变。
- **`FR-ORD-003`**：候选根与复刻写入用的是同一份顺序：当前项目的 `.dsh/skills`、当前项目的 `.agents/skills`、`DSH_HOME`（默认 `~/.dsh`）下的 `skills`、`DSH_AGENTS_HOME`（默认 `~/.agents`）下的 `skills`。同名在多个根里都存在时取**第一个**命中的目录，顺序必须确定、可复现。
- **`FR-ORD-004`**：拼路径之前必须先按 Skill 名的合法形状（小写字母 / 数字 / 连字符，≤128 字符）过滤；含 `/`、`..` 或空白的一律跳过，**不得**把它们当路径用。
- **`FR-ORD-005`**：读不到时间的 Skill **排在最后、按名称排序**；两个都读不到时也按名称。有真实时间的永远压过没有时间的。**不得**用 mtime、当前时间或任何别的时钟顶替一个读不到的时间。
- **`FR-ORD-006`**：卡片必须把两件事**分开**说：`MM-DD 加入本机`（**只到日**，跨年才带年份；**不许**显示时:分，也**不许**写「今天 / 刚刚 / 几分钟前」——2026-10-03 用户：「我交互体验将来只需要有月日就行」，谁更新由**列表顺序**回答），以及**只有存在复刻血缘时**才多一行 `复刻自 <来源 Skill>`。「什么时候来的」与「从哪来的」是两类事实，**不许**合并成一句含糊的「创建时间」。
- **`FR-ORD-007`**：列表上方有一句话说明按什么排：有时间时说「按加入本机的时间倒序：最近加入的排在最前。」；有读不到时间的时候要**报数**（「另有 N 个 Skill 读不到加入时间，按名称排在最后。」）；一个都读不到时说「读不到加入本机的时间，这里按名称排列。」。响应里没有 `ordering` 时**整句不出现**——不许从看到的第一行倒推顺序。
- **`FR-ORD-008`**：`ordering.addedAtKnown / addedAtUnknown` 统计的是**整个目录**，不是这一次搜索过滤之后的结果：换一个搜索词不得改变「这台机器上有几个 Skill 说得出来加入时间」。
- **`FR-ORD-009`**：三种「读不到」要如实分开，用限制码表达：`added-at-unavailable`（一个都读不到）、`added-at-partial`（只读到一部分）、`lineage-unavailable`（宿主没给出可读的血缘）。**「没有复刻过」与「读不到复刻记录」不许混为一谈**：后者还要多一句「读不到复刻记录，所以卡片上没有「复刻自」那一行。」。
- **`FR-ORD-010`**：排序**不新增路由**：宿主仍是 **12 条**（`0.9.2` 口径；V1.0 起是 **13 条**，见 §5.13），`GET /skill-trace/catalog` 的响应新增 `ordering`，每个 Skill 新增 `addedAt` 与 `lineage`；两处读盘（目录 birthtime、血缘库 `list()`）都是只读，失败**不抛错**、按 §5.11 的限制码降级。要再加路由必须同时改 `AGENTS.md` §6.12 与 `spec/SDD.md` §3。
- **`FR-ORD-011`**：已知限制如实登记：这个排序说的是「**文件什么时候出现在本机**」，不是「作者什么时候写的」、不是「最后一次修改」、也不是「用过几次」；被复制 / 解压 / 同步过来的目录会带着各自的 birthtime。它**不**提供历史版本对比，也**不**提供用户自定义排序（顺序不是偏好，不写进偏好存储）。
- **`FR-ORD-012`**：`FR-SKL-007` 的客户端本地搜索与 `FR-SKL-008` 的字段边界不变：排序只改顺序，不扩投影白名单，也不把收据或学习状态带进这个列表。
- **`FR-ORD-013`**：卡片元信息里**只说例外，不说默认**（2026-10-03 用户：「模型可调用、可用 `/name` 调用，这两个是不是重复？」——不是重复，DSH 的两个开关彼此独立、四种组合都合法，但真机实测 69 个 Skill 全是 `{modelInvocable:true, userInvocable:true}`，于是每张卡都在重复同一句恒为真的话）：①调用方式**只在开关为 `false` 时**出字（「不可由模型调用」/「不能用 `/name` 调用」），默认成立的组合一个字都不写；②`provider` 为默认的 `filesystem` 时不写，只有插件等非常规来源才写出来。载荷里缺字段（`undefined`）**不得**被念成「不成立」——那是编出来的断言，判断用严格的 `=== false`。

### 5.12 Skill 实例验收（`FR-INST-*`）

> **本节是 V0.10.0 的规格，已随 `0.10.0` 发布**（用户 2026-10-03 给出的 V0.10.0 规格；本节只写产品语义，技术契约见 `spec/SDD.md` §21）。它**不新增页面、不新增导航、不新增 Route、不新增第二套 Agent Runtime**。

`FR-INST-*` 回答的是**「我刚刚改的这个 Skill，在一个真实任务里有没有按照预期工作？」**——这是**人在一个干净会话里做的验收**。插件负责**生成一个针对这次修改的真实测试任务与观察项**并交给用户；**它不运行 Skill、不读结果、不判定成功**。

三层必须分清：**静态 Skill 验收**（§5.9：结构、格式、资源、平台约束对不对）→ **Skill 实例验收**（本节：这次修改在真实任务里是否按预期工作）→ **Skill Evaluation**（V1.0+：把实例验收升级成可重复的 Case 与 Run，并把同一个 Case 的 Before / After 并排摆出来；**不做分数与「稳定提升」这类结论**，方差只以「哪些事实一致、哪些不一致」的形式出现在 V1.1；本版**不做**）。

- **`FR-INST-001`**：**生成与判定分家。** 插件只做两件事：生成测试任务与观察项、把静态验收结论摆出来。运行 Skill、观察实际结果、判定是否达到预期，全部由**用户在新会话里**完成。插件**不自动运行、不等待、不读结果、不判定、不打分**。
- **`FR-INST-002`**：能力名统一为 **「Skill 实例验收」（Skill Instance Test）**。**本版（V0.10.0）不许**把这一块叫 Skill Run / Skill Execute / Skill Benchmark / Skill Evaluation / Skill 自动测试 / Skill 质量评分——本版做的不是评测系统。**`Skill Evaluation` 这个名字留给 V1.0 的正式能力**（§5.13），V0.10 不许借用；反过来，V1.0 也只能用这个名字，不许改口叫「评分」「打分」「评测分数」。
- **`FR-INST-003`**：**只针对「本次修改」生成。** 必须已经有一次修改事务（即「本次修改对比」可用）时这一块才有意义；没有修改事务时**整段不渲染**（与 `FR-MOD-011` 同一条 gate：常驻的空卡会被读成一种状态）。首版**不做**「对任意已安装 Skill 生成泛化测试」。
- **`FR-INST-004`**：**「基于修改生成」是硬要求，不许退化成通用模板。** 生成的输入必须综合：用户修改意图 + 修改范围（scope）+ 修改前后 diff + 当前 `description` + 框架（Framework）+ 静态验收结论。界面上要说的是「**针对你刚才修改的 Skill，这个任务可以直接验证修改是否生效**」，而不是一条通用的 Skill 使用示例。
- **`FR-INST-005`**：**测试 Prompt 与观察项物理分离，且 Prompt 不许反过来教 Agent。** 复制给 Agent 的那段正文里**不得出现**：本次 diff 的变更小节标题、范围（scope）标签、「本次修改」「你刚才修改了……」这类元话语、`SKILL.md` 里的步骤名或答案。否则等于在 Prompt 里把 Skill 该怎么做重新讲一遍，测的就不是 Skill。**这条要做成测试守卫。**
- **`FR-INST-006`**：Prompt 的结构是：任务 + 工作目标 + 输出要求 + 注意（「直接完成任务，不需要解释你为什么选择某个 Skill」「按当前环境中的 Skill 能力完成任务」）。**「验收关注点」不进 Prompt**——它只给用户看，塞进 Prompt 会污染测试。
- **`FR-INST-007`**：**观察项只许写成观察句与疑问句**（「是否实际使用了相关 Skill」「关键流程是否被执行」「本次修改涉及的行为是否体现」「原有核心能力是否保持」），**不许**写成断言。§5.5 的禁用词纪律在这里同样生效：界面任何位置不许出现「已执行 / 未执行 / 已完成 / 未完成 / 已加载 / 已读取 / 已生效」。
- **`FR-INST-008`**：内部支持三种测试意图——**Core**（验证本次修改最主要的目标）、**Boundary**（验证修改不会在边界条件下失效）、**Regression**（验证旧能力没被破坏），但**界面第一版只给一个按钮、只生成一个综合 Prompt**（Core + Boundary + Regression 合起来），不做三个按钮、不做测试任务列表。
- **`FR-INST-009`**：**Regression 约束只能来自「没有被本次 diff 触及的声明能力」**，并逐条具体（例如原有输出结构、原有核心约束、原有资源使用规则）。**禁止**输出「确保原有能力没有受到影响」这类笼统句；拿不到相应信息时如实进入 `unavailable` / `limitations`，**不假装生成了一条完整的回归约束**。
- **`FR-INST-010`**：六个修改范围的观察重点各不相同：`skill-md-rules` 看规则是否真正生效；`skill-md-workflow` 看流程顺序与步骤约束是否真正体现；`skill-md-description` 看触发场景是否发生变化；`references` 看真实任务里相关 reference 是否**被实际使用**；`scripts` 看真实任务是否**触发并体现了**本次涉及的脚本能力；`assets` 看真实任务是否**需要并体现了**本次涉及的资源能力。
- **`FR-INST-011`**：**证据原则在三个资源类范围上继续贯彻**：观察不到证据**不能**推断没有执行；`SKILL.md` 里声明存在**不能**推断运行时实际使用了它。插件**不自动执行** `scripts/`、**不自动判定**脚本是否执行成功、**不因**声明了某个脚本或资源就推断它被用上。
- **`FR-INST-012`**：**不许出现任何形式的自动判定**：「本次 Skill 修改成功」「成功率 92%」「Skill 质量：优秀」「修改有效」以及任何通过率、评分、排名都不许出现。插件最多只能说「**已生成实例验收任务**」加上静态验收结论。
- **`FR-INST-013`**：**不自动运行。** 不自动创建新会话、不自动发送 Prompt、不等待 Agent 完成、不读回结果、不判定。理由是 DSH 已有原生 Agent 会话机制，没有必要复制第二套 Agent Runtime；第一版要验证的是「测试 Prompt 能否有效验证这次修改」，不是先做自动化框架。界面上只给一句很弱的辅助提示：**建议在新的 DSH 会话中运行，以避免当前修改对话的上下文影响测试结果。**
- **`FR-INST-014`**：生成结果**只保存在当前详情页的前端状态里**（与本次修改、本次 diff、静态验收同级），页面刷新后可以重新生成，**不要求**第一版保存测试历史。**不新建**数据库、Test History、Test Runs、Evaluation Database、Benchmark Dataset。
- **`FR-INST-015`**：**不新增页面、不新增导航、不新增 Route、不新增第二套 Agent Runtime。** 复用现有 Skill Detail、「本次修改对比」卡与已有数据流；宿主仍是 **12 条**路由。原设计里的 `POST /skill-trace/instance-test` **取消**。
- **`FR-INST-016`**：**模型只能在「生成测试任务 / Prompt」这件事上参与**，不许参与自动运行、自动判断、打分或宣布有效。当前架构没有合适的模型调用入口时，第一版**优先复用现有能力**，不为它新建一套模型调用基础设施。
- **`FR-INST-017`**：界面位置固定在详情页主列的 **Skill Evolution → 本次修改 → 本次修改对比 → 实例验收**，作为「本次修改对比」卡**内部的下一段**；只有 `comparison` 存在时才出现。**不新建「测试中心」**，不新建一级 / 二级页面。
- **`FR-INST-018`**：**诚实边界。** diff 读不到、静态验收落到「无法判断」、框架读不到时，逐项进 `unavailable` / `limitations` 并说清缺的是哪一项；**不产出一个看起来完整的 Prompt**。
- **`FR-INST-019`**：**本版不做**，把运行证据层留给 V1.0 的 Skill Evaluation（§5.13）。要分清 V1.0 **会做**什么与**永远不做**什么：**会做**——运行历史（可重复的 Case 与 Run 记录）、Baseline / With Skill 与 Before / After 对照、四段证据与逐条断言；**不做**——Benchmark 排名、自动评分、自动成功判断、Evaluation Dashboard、「Skill Score」这类标量结论（`FR-EVAL-012` / `FR-EVAL-014` 已把它们写死为禁止项，不属于「以后再说」）。本版也**不把实例测试结果自动接回** Skill Detail。
- **`FR-INST-020`**：**终验判据**（用户原话）：**必须能证明「生成出来的 Prompt 真的是针对这次修改的」，而不是做了一个漂亮的通用测试 Prompt 生成器。**
- **`FR-INST-021`**：**生成器是一支零依赖纯函数**（`src/core/skill-instance-test.mjs`）：不 `import`、不读文件系统、不访问网络、**不调用模型**、不执行 Agent、不改 Skill、**不持久化测试历史**、不读时间也不掷骰子——同一份输入永远得到逐字节相同的结果。只有这种形态，「生成的 Prompt 真的针对这次修改」才是**可断言、可守卫、可复核**的（`FR-INST-020` 的前提）。模块同时导出 `buildSkillInstanceTest` 与规格里那个建议名 `buildInstanceTest`（别名）。
- **`FR-INST-022`**：**六项输入逐项如实记录，界面要看得见。** 结果里必须带一份 `trace`：这次生成**真正在场**的那几项输入（用户修改意图 / 修改范围 / 修改前后对比 / Skill 描述 / 框架 / 静态验收结论，顺序固定、不在场的不列）与**主范围从哪来**（用户意图点名了某个**确实被改动过**的范围时听意图，否则按固定优先级取第一个改过的范围）。详情页的「这个任务是怎么来的」要把这两句话念出来——这是把研发侧的「可追溯」变成用户能读的一行字。
- **`FR-INST-023`**：**用户意图只用于对齐任务形状与记录来源，原文一个字节都不进结果。** 意图既不许出现在复制给 Agent 的 Prompt 里，也不许出现在观察项、回归约束或 trace 文案里；**diff 自己的变更小节标题**同样不许进 Prompt。理由与 `FR-INST-005` 相同：把「你刚才改了什么」写进去，等于在 Prompt 里重新教一遍 Agent。**这条要做成测试守卫。**
- **`FR-INST-024`**：**回归约束优先来自框架（Framework）的声明能力**，并排除「标题被本次 diff 触及」或「角色对应到被改动的范围」的小节（范围 → 角色的映射由 `INSTANCE_TEST_SCOPE_ROLES` 固定）；框架里一条都取不到时才退回 `SKILL.md` 正文的二级小节，并如实注明这次是从正文取的。**缺框架不使生成不可用**，只进 `limitations`（不可用只有四种情形：没有本次修改对比、对比不可用、改动没落在可测范围、读不到 Skill 正文）。
- **`FR-INST-025`**：**卡面结构与抬头固定**：`验证目标`（一句话说明验证的是「本次修改是否改变了这个 Skill 的实际行为」）→ `本次修改`（沿用 §5.10 的范围标签）→ `测试 Prompt`（可滚动的正文 + `[复制测试 Prompt]`）→ 建议在新会话运行 → `预期观察点` → `回归约束` → 「这个任务是怎么来的」（折叠）。只有 `comparison` 存在时才渲染，且**没有生成前一个 Prompt 都不画**。
- **`FR-INST-026`**：**任务句是一句指派，不是一段描述；过长的文字按词边界截断。** `【任务】` 不许整句照搬 Skill 的 `description`（那样读起来像「这个 Skill 是干什么的」），要写成「请完成下面这件真实工作，要真的做出来，不要只讲怎么做：…」这类**指派**口吻；描述本身过长时走同一个 `clip()` **按词边界**截断（找得到空格就从最后一个完整词后断开，中文没有词间空格才退回按字符截），**不许切出 `…to avo.` 这种半个单词**。回归约束那句引用声明能力时同样走 `clip()`。

### 5.13 Skill Evaluation（`FR-EVAL-*`，V1.0，已随 `1.0.0` 发布）

> **这一节里 V1.0 的部分已随 `1.0.0` 发布**（见本文件头部「版本与实测状态」与 §10.2）；**V1.1 及以后的条目仍是路线与需求，不是现状**：每一条在实现、守卫与真机验收之前，**都不得在任何界面、README、CHANGELOG 或发布说明里被当作已具备**。它的价值在于：在动手之前把「这一版不做评分器」这句话拆成可执行的边界。
>
> **外部依据（逐条核过原文，2026-10-03）**：`SWE-Skills-Bench`（arXiv 2603.15401）实测 **49 个公开 SWE Skill 里 39 个对通过率零增益，平均只有 +1.2%，3 个把表现拖低最多 10%，token 开销最高 +451%**；综述 `Agent Skill Evaluation and Evolution`（arXiv 2606.11435）指出既有指标「忽略 token 成本、延迟与错误类型」，且 §4 明确 **no existing benchmark evaluates evolution longitudinally**。官方生态里把评测闭环放进 Skill Creator 的是 **Anthropic**（`anthropics/skills` 的 `skills/skill-creator/SKILL.md`：`eval` / `baseline` / `with-skill` / `assertion` / `variance` / `trigger eval` 都在，带 `aggregate_benchmark.py` / `run_eval.py` / `grader.md` / `comparator.md`）；**OpenAI** 的 `skill-creator/SKILL.md` 只有 `quick_validate.py` 与「按真实使用迭代」，**没有**任何评测闭环。

- **`FR-EVAL-001`**：**V1.0 要把 V0.10 的一次性实例验收升级成可重复的实验与对照。** V0.10 生成的那份任务 Prompt 用完就散落在会话里；V1.0 让它成为一个**可以反复使用的 Case**，并把每次运行的条件与可观察事实并排摆出来。**这一版仍然不做评分器**——见 `FR-EVAL-014`。
- **`FR-EVAL-002`**：**四个模块的落地顺序固定**：**Evaluation Case → Evaluation Run → Comparison → Runtime Evidence**。证据层是**解释层**，最后做；否则界面会先长出位置、再没有事实可填。
- **`FR-EVAL-003`**：**Evaluation Case 的对象定义**：`{caseId, 任务 Prompt（沿用 §5.12 的四块结构与全部禁用词纪律）, 预期观察点（≤6 条疑问句）, 回归约束, 生成器版本, skillFingerprint, scopeIds}`。`caseId` 必须是**纯函数**：`sha256(任务 Prompt + Skill 指纹 + scopeIds + 生成器版本)`——**不含时间、不含随机数、不含会话 id**。哈希由**宿主层**计算（生成器保持 `FR-INST-021` 的零 `import`，不自己引 `node:crypto`），但生成器输出的那几项内容必须**足以唯一决定** `caseId`。否则「可重复」只是一句愿望。
- **`FR-EVAL-004`**：**Case 与生成它的那一版 Skill 绑定，且不许说「过期」。** Skill 再改一次后，旧 Case 的标注是「针对 `<该版指纹>` 的 Case」，**不许**写「已过期 / 已失效」——它测的是那一版的行为，历史事实不会过期；新 Case 是**另一个 Case**，不是旧 Case 的替代品。
- **`FR-EVAL-005`**：**Case 仍由确定性生成器产出，不引入模型生成 Case。** §5.12 `FR-INST-021` 的全部约束（零依赖纯函数、不 `import`、不读文件系统、不访问网络、不调用模型、不读时间、不掷骰子）继续生效；V1.0 只**多记一份 `生成器版本`**，不改生成方式。
- **`FR-EVAL-006`**：**Evaluation Run 记录的就是实验条件**：`{runId, caseId, 开始时间, turn / step 游标, provider, model, reasoningEffort, DSH 版本, 插件版本, observedInstructionSha256, currentInstructionSha256, match, 加载证据（status / callSeq / resultSeq）, runtimeEvents 汇总}`。**字段名沿用源码**（`src/core/source-snapshot.mjs:179-181` 的 `observedInstructionSha256` / `currentInstructionSha256` / `match`），不另起名字。**缺项一律写 `unavailable`，不许用默认值或推断值填补**——这一版的全部可信度都建立在「缺就承认缺」上。
- **`FR-EVAL-007`**：**模型与 Provider 是新增的读取点，只读元数据。** 来源是会话事件里的 `request/context`（`{provider, model, contextWindow}`）与 `request/header.header.config`（`LlmCallConfig {provider, model, reasoningEffort}`）；**只读这几个字段**，不读 prompt 正文、不读工具参数与结果内容（`AGENTS.md` §6.9 继续生效）。**命名必须分开**：LLM 运行侧的 provider 与 Skill **来源** provider（`filesystem` 等）不得共用一个词，界面上要能一眼看出哪个是「模型」，哪个是「Skill 从哪来」。
- **`FR-EVAL-008`**：**DSH 版本今天还没有已验证的读取方式，实现前必须先定下来并实测。** 插件位置**解析不到** `@deepseek-ai/dsh`：2026-10-03 在真机路径上实测 `createRequire(插件文件)('@deepseek-ai/dsh/package.json')` → `MODULE_NOT_FOUND`（`~/.dsh/profiles/core-020/node_modules/dsh-skill-trace` 是指向工作树的符号链接，向上查找链里没有这个包），所以**不许**照抄「运行时能直接 require 到版本」这个结论。候选路径：读运行 profile 的 `package.json` / 其 `node_modules/@deepseek-ai/dsh/package.json`（`DSH_HOME` 在宿主里可得），或由宿主注入版本常量。**定不下来或读不到就写 `unavailable`**——这条是「同一个 Skill 在两台机器上结果不同」唯一能自查的线索，宁可承认没有。
- **`FR-EVAL-009`**：**时间优先取事件自带的时间**：事件信封的 `time`（epoch ms）为准，`Date.now()` 只在缺失时兜底。`turn` / `step` 是**日志顺序游标**，界面与文档都**不得**把它说成时间或「第几轮对话」。
- **`FR-EVAL-010`**：**Runtime Evidence 的四段固定为 Trigger → Load → Use → Outcome，每段只说它够得着的话**：
  - **Trigger**：这次会话里 DSH **向模型提供过**这个 Skill（`catalogPublished`）——这是事实，不是推断；
  - **Load**：**在 seq N 拿到了指令正文**，附 `sha256` 与文件指纹 `match` / `mismatch` / `unavailable`——这是**协议级证据**，但它只证明「这些字节进入了模型可见对话」，**不证明模型采用了它**；
  - **Use**：本次运行里出现了哪些工具活动（**仅元数据，无参数无结果**）以及用户 / Agent 的陈述；**不许**写成「模型用了它」；
  - **Outcome**：**只能来自用户判定或 Agent 自报**，逐条标来源，**插件不判定**。
- **`FR-EVAL-011`**：**三条不等式做成界面上的固定说明句**（不能只写在文档里）：「**加载 ≠ 使用**」「**使用 ≠ 结果**」「**结果 ≠ 这个 Skill 造成的**」。理由与 `FR-INST-011`、`FR-INST-012` 同源：不能因为最后成功就说这个 Skill 有效。
- **`FR-EVAL-012`**：**断言（Assertion）逐条列出，每条三个字段**：`陈述` + `结论（通过 / 未通过 / 无法判断）` + `来源（协议事实 / 用户判定 / Agent 自报）`。**禁止任何聚合**：断言通过率、n 次通过次数、平均分、稳定性百分比、方差与标准差、Skill Score、排名、趋势图**一律不许出现**（与 §2.3 同一条）。
- **`FR-EVAL-013`**：**Comparison 只许「同一个 Case」的两轴**：**Before Skill vs After Skill**（同一 Case、同一 Skill 的两个版本）与 **Baseline vs With Skill**（同一 Case、同一模型条件，有 / 无该 Skill）。**禁止**把两个不同任务、两个不同 Case 的运行并排比。界面要回答的是用户原话那串问题：「同一个任务下，改前发生了什么、改后发生了什么、Skill 有没有加载、运行时看到了什么、哪些断言通过、哪些仍无法判断」——而不是「Skill Score 87」。
- **`FR-EVAL-014`**：**不做评分器（这条是整个版本的护栏）**。理由不是「不想做」，而是**外部证据不支持标量判断**：49 个公开 SWE Skill 里 39 个零增益、平均 +1.2%、3 个负增益、token 开销最高 +451%（`FR-EVAL-001` 上方引文）。所以本产品只做**证据链**：哪次运行、什么条件、加载了什么、观察到了什么、哪些断言通过、哪些仍无法判断。**任何形式的「Skill 好 / 坏」「有没有用」标量结论都不许出现。**
- **`FR-EVAL-015`**：**不自动跑。** 不自动创建会话、不自动发送 Prompt、不自动重复 n 次、不读回模型回复正文、不由插件调用模型做任何判定。运行由**用户在新会话里**完成，插件只负责记录与对照（继承 `FR-INST-013`）。
- **`FR-EVAL-016`**：**存储与路由需要明确授权（V1.0 开工前必须先拿到）。** Case 与 Run 要**落盘**，就需要**一个新的本机存储**（沿用 `docs/PRIVACY.md` 的 `0700` 目录 / `0600` 文件 / 临时文件 + 原子 rename / 禁字段清单）与**一条新的 POST 路由**（届时同步 `docs/PRIVACY.md`、`spec/SDD.md` §3 与 §11 与契约守卫）。`sessionId` 不进落盘内容；跨会话对照用 `caseId + runId`。**这是 V0.8 以来第一次新增落盘内容（用户的任务正文与用户判定），不得在未获授权的情况下实现。**
- **`FR-EVAL-017`**：**保留与清理策略必须与 V1.0 一起定**：run 历史的条数上限、按 Case 清理、按 Skill 清理、以及删除后残留什么。否则 V1.3+ 的逐版演进评测面对的是一堆无主数据。
- **`FR-EVAL-018`**：**后续版本边界（避免混版）**：**V1.1** = Skill Regression / Variance，把**多 Case 套件 × 重复 n 次**的意义限定在「**哪些事实一致、哪些不一致**」，**不给方差数值、不给稳定性分数**；**V1.2** = Skill Trigger Evaluation，`should-trigger` / `should-not-trigger` 场景集，「被提供」「被加载」可测，「该不该触发」由用户判定；**V1.3+** = Skill Evolution Evaluation，沿血缘逐版对照来回答「这个 Skill 有没有在一轮轮反馈里变好」——综述指出这一格**目前没有任何 benchmark 在做**，方向由 `FR-EVAL-017` 的数据保留策略支撑。

## 6. 关键交互与页面状态

### 6.1 偏好迁移

读取偏好 version 3。取值恰好 `current` / `installed`；无版本号、或值属于 v0.5 词汇（`skills` / `map` / `receipt` / `audit`）时，按「从未表达偏好」处理并归一化为 `current`。**「本次 Skill」是默认第一屏，这条不得被历史偏好夺回。**

### 6.2 列表与搜索

- 「本次 Skill」读收据的 load evidence，回答「这次对话用了什么」；
- 「已安装 Skill」只读 `GET /skill-trace/catalog`，由 `buildInstalledView` 投影，回答「本机 / 当前作用域能发现什么」，**刻意不读收据**；
- 客户端搜索框按名称与描述实时过滤，**不请求 Host**；
- 「已安装 Skill」的顺序由响应里的 `ordering` 描述（§5.11）：按**加入本机的时间**倒序，读不到时间的按名称排在最后；列表上方那句话与卡片上的 `MM-DD 加入本机` / `复刻自 X` 都只是把宿主下发的事实念出来，客户端**不排序、不猜时间**；元信息里默认成立的调用方式与 `filesystem` **不写**（`FR-ORD-013`）；
- 列表负责选择、详情负责完整阅读：列表首屏不读 `SKILL.md` 全文，进入详情才读。

### 6.3 进入详情与返回

点任意一张卡（两个列表都适用）→ 打开唯一 Skill 详情并记住来源列表 → 返回文案由来源 state 派生。从「已安装 Skill」的卡片进入时，**整张卡就是入口**（键盘可达、有 hover 与 focus 态），不再额外配一个「查看详情」按钮。

### 6.4 详情页阅读顺序与折叠

左栏三张卡（Skill 摘要 / Definition 事实 / Repository）+ 右栏文档面板，主内容区依次为 框架 → 本次运行逻辑 → 步骤证据 → `SKILL.md`。渐进披露遵循「列表负责选择、详情负责完整阅读」：默认展示结论、状态与下一步，证据按需展开；展开内容必须占完整可读宽度；多条记录不得为了整洁而静默聚合或丢失，**聚合必须报数**。

### 6.5 中文阅读版的交互

点「中文阅读版」→ `POST /skill-trace/translate` 单次 `ctx.llm` 调用。成功则段控可切原文 / 中文阅读版，Outline 跟随当前版本；失败则段控**回到原文**、错误保持可见并可重试。保存态由响应里的 `saved` 布尔驱动：成功显示 `✓ 中文阅读版已保存（本地保存）`，未写成本机则显示「中文阅读版没有保存到本机，下次打开需要重新翻译。」——用 `--st-warning` 表达，不是装饰性状态。

### 6.6 复刻的交互

详情页左栏对象区里**唯一的对象级动作**是「复刻 Skill」（不并排 编辑 / 创建 / 优化 / 收藏 / 学习；`sha` 读不到时禁用并在 `title` 里说明原因）。对话框：标题 + 一句副标题、目标名称输入、保存范围（当前项目 / 我的 Skill）、复刻内容（完整 Skill / 仅 `SKILL.md`）、来源与当前指纹、取消 + 确认；宽 560px、紧凑、≤12px 圆角、**不出现第二个竞争主按钮**；打开时不许出现任何「已创建」字样；校验就地提示，不弹 `window.confirm`。结果态：`✓ Skill 已创建`、目标名、写到哪个范围、复刻内容与文件数、目录刷新状态、来源是否被改动、`limitations` 列表、调用方式 + 复制按钮（复制按钮只写剪贴板，不注入输入框、不发送、不触发 Agent）。

### 6.7 页面状态

| 状态 | 要求 |
|---|---|
| Loading | 保留页面上下文或显示单行轻量状态；状态点轻量呼吸；`aria-live="polite"`；`prefers-reduced-motion: reduce` 时停止持续动画 |
| Empty | 必须区分六种：当前会话没有已加载的 Skill / 当前会话没有可重建的运行证据 / 当前作用域没有可发现 Skill / 搜索或筛选无匹配 / Registry 或目录不可确认 / 尚未选择 Skill。**不得统一写成「暂无数据」**；「筛掉的画布不是空状态」 |
| Error | `role="alert"`；提供重试 / 返回 / 检查来源等恢复动作；以边框和文字色表达，不使用大面积高饱和红底；**组件在渲染期抛异常必须被捕获并显示可读错误**，不得让整块界面变空——空面板不是错误状态 |
| Ready | 当前选择必须同时有结构、文字或边框反馈；局部数据更新不把用户踢回列表顶端；不自动打开危险操作或替用户做人工判断 |

### 6.8 保存、清除与错误

**点击、发起请求或触发浏览器下载不等于完成；成功态必须来自 Host 已提交并可回读的结果。** 保存后在原位显示成功结果（Toast 不能作为唯一反馈）；Busy 时禁用重复提交并保持按钮宽度稳定；清除必须说明将删除什么、保留什么，并提供确认与取消；错误必须写清发生什么以及用户如何恢复；**UI 不显示本地绝对路径、凭据、内部堆栈或完整 Skill 正文**。

### 6.9 可访问性

所有按钮 / 筛选 / 列表项 / 折叠节 / 展开控件可键盘访问；折叠章节使用原生 `<details>` / `<summary>`；`:focus-visible` 使用 2px 品牌色外框和 2px 偏移；选中使用 `aria-pressed` 或 `aria-current`；Loading 容器使用 `aria-busy`；错误使用 `role="alert"`；对象名可在列表省略但详情必须展示完整内容；用户输入与路径使用 `overflow-wrap:anywhere`；不得移除 outline 后不补焦点样式。窄窗（`<460px`）控件最小 44px、编辑控件 16px、表单单列。关键动作必须带文字，**不使用 emoji 代替正式图标**。

## 7. 异常与边界场景

| 场景 | 必须的行为 |
|---|---|
| 当前观察尚未到可靠边界 | 保持 `requested`，不提前写成功或失败 |
| 恢复事件 `TOOL_OUTCOME_UNKNOWN` | `outcome-unknown`，显示「结果未知」 |
| 恢复事件 `TOOL_NOT_STARTED` | `not-started`，显示「未开始」 |
| Skill 返回错误 | `failed`，保留错误类别，不默认保存完整错误正文 |
| Registry snapshot 不完整 | 已安装列表显示覆盖未知，**不得显示确定总数** |
| 单条事件无法识别 Consumer | 显示「Consumer 身份不可区分」，不影响标准事件本身的加载事实 |
| Session 崩溃或中断 | 依据 DSH 补写的恢复结果区分「结果未知 / 未开始」 |
| 本地收据写入失败 | 显示可恢复错误并允许重试，不影响原生会话 |
| Skill 定义正文变化 | 指纹比对结论变为「文件已改变」；若已有中文阅读版，按 `definition-changed` 失效并要求重新翻译 |
| 只有一侧有指纹 | 写「无法比对」，**不得**写「文件已改变」或「Skill 已失效」 |
| 定义正文不可读 | 右栏降级为可见错误状态（一句说明 + 重试），**不卸载整个 Tab**，左栏其余事实照常显示 |
| 定义缺少 `description` | 显示「该 Skill 没有提供足够清晰的用途说明」，不调用模型补写 |
| 请求字段缺失或类型错误 | 该字段局部降级为可见错误，页面不得整体崩溃或空白，也不得静默当空值 |
| Repository 无法解析 | 显示「未解析」，不伪造链接、不留禁用态占位 |
| Repository 地址带凭据或是本机绝对路径 | 整条拒绝展示，只显示「未解析」 |
| 翻译请求失败（模型不可用 / 超时 / 输出不合规） | 段控回到「原文」，错误保持可见并提供重试，禁止静默失败 |
| 翻译期间定义变化 | 返回 `definition-changed`，丢弃译文，提示「Skill 内容已变化，请重新翻译」 |
| 译文未通过 inspection（fence / 标题层级 / inline code / URL / 路径不匹配） | 报告违规项，不得把译文当作原文的等价替代 |
| 复刻目标名已存在 | `409`，就地提示改名，**不覆盖、不自动改名、不先删后写** |
| 复刻源指纹与前端读到的不一致 | `409`，提示重新打开详情页——源在用户读它的这段时间里变了 |
| 复刻半途失败 | 删掉刚建的目录并如实报错 |
| 复刻完成后观察不到目录刷新 | 写「目录刷新状态待确认」并说明重启后可见，**不得声称已刷新** |
| 已安装列表作用域完整但无发现结果 | 明确空态，不显示会话收据或虚构目录 |
| 作用域覆盖未知或读取失败 | 「暂时无法确认完整 Skill 列表」，不得显示确定总数 |
| 搜索无匹配 | 「没有匹配的 Skill」，与上两者区分 |
| 当前页面没有已挂载的普通会话 | 允许进入「已安装 Skill」；当前会话区域显示「需要进入一个会话后确认」，不得冷启动 Agent 只为取目录 |
| 删除一张会话收据 | 明确提示删除范围并二次确认，不影响 DSH 原生数据 |
| 删除全部本地数据 | 明确列出收据与偏好范围，二次确认后统一删除 |
| 插件被关闭 | 停止新增 Trace；历史本地收据仍按产品设置处理；DSH 原生行为不变 |

**所有「读不到」都必须说人话**：不许显示裸错误码，也不许沉默。

## 8. 数据与隐私要求

### 8.1 默认允许保存

产品自己的 ID、Schema 版本与时间；Session 标识及 Turn / Step / 事件序号；Skill 名称、Provider、脱敏来源标签、版本或 SHA-256；加载状态、Observer 类型与覆盖状态；Skill 的发现状态与定义可读状态（当前 sha256、本次会话加载次数、请求版本与当前版本的比对结论）；中文阅读版的译文（按 `FR-UI-060` 落盘，键不含会话）；旧版本 `humanAssessment` 与旧版本写入的学习笔记 / 改进意图 / 验证计划 / 验证结果继续留在既有收据文件中，**只为不破坏既有数据**，无任何 UI 读写路径。

**V0.8 新增允许保存的只有「Skill 复刻血缘」**（见 §5.7 `FR-EVO-002`）：来源与目标的 Skill 名、来源正文的 `sha256`、复刻模式、保存范围、复刻时间、目录观察状态，以及**已被确认**的仓库来源标签；落在插件自己的 `<dataRoot>/lineage/`，**一个目标 Skill 一条记录**。它**不是**收据里那个 `lineage`（那是会话父子血统），两者不得混用（`FR-EVO-008`）。

### 8.2 默认禁止保存

完整 Prompt、Assistant 回答与 Tool 输出；完整 Skill 正文和资源文件；Token、Cookie、密钥、环境变量值；未脱敏绝对路径；项目文件正文或自动抓取的工作区内容；从用户任务正文自动生成的未确认标签；自动从 Prompt / 回答 / 项目正文生成的个人理解。

中文阅读版：**永不写回 `SKILL.md`，永不进入收据、备份、`localStorage`、`sessionStorage`、会话日志或用户对话**；只以 `FR-UI-060` 定义的本机资产形式落在插件自己的数据目录里。

**V0.8 的差异比较不落盘任何东西**：Diff 每次实时从当前文件系统读取两侧正文与资源清单，算完即弃。血缘记录里也不许出现正文或资源内容（`FR-EVO-002`）；差异面板不返回、不显示绝对路径（`FR-EVO-019`）。

### 8.3 本地数据原则

- 本地优先，不依赖远程服务；
- 写入采用插件独立存储，**不修改 DSH 原始 Session 日志**；
- 失败时保留可重试状态，不静默丢失、不伪造成功；
- 删除必须由用户发起并确认范围；
- 唯一的出网行为是**用户显式触发的翻译**（把当前 Skill 的定义文本发给用户自己配置的 DSH 模型 provider 一次），其余数据不出本机；
- 移除插件不会自动删除已有本地收据；删除应始终由用户在产品内明确确认。

## 9. AI 与自动分析边界

**只有一处模型调用：用户显式触发的「中文阅读版」翻译。** 边界：

- 只翻译当前 Skill 的 `SKILL.md` 定义正文，单次只译当前 Skill，不自动、不批量；
- 通过 `ctx.llm` 调用**用户自己配置的 DSH 模型**，不引入插件自有模型、密钥或服务端；
- 必须向用户明说定义文本会发送到该模型 provider，除此之外不出本机；
- 不得把完整 Session Prompt / Tool 输出 / Cookie / credential 作为翻译上下文，不得向用户对话追加「请翻译……」一类消息；
- 译文绑定 `sourceSha256`，失败可见且可重试，禁止静默失败。

**其余一切分析都是确定性的、不调用模型**：

| 产物 | 实现 | 性质 |
|---|---|---|
| 本次加载证据 | `trace-reducer.mjs` | 从事件投影，纯函数 |
| 已安装列表 | `installed-view.mjs`（`buildInstalledView`） | 从 registry snapshot 投影 |
| Skill 框架 | `src/core/skill-framework.mjs` | 关键词表分类，纯函数、无依赖 |
| 声明流程 | `skill-flow.mjs` / `definition-outline.mjs` | 标题层级 + 有序列表双通道抽取 |
| 本次运行逻辑 | `src/core/skill-runtime-logic.mjs` | 从当前收据推出 |
| 步骤证据 | `src/core/flow-evidence.mjs` | 封闭五值词表 |
| 指纹比对 | `runtime-fingerprint.mjs` | 纯哈希比较 |
| 仓库来源 | `repository-resolver.mjs` | 三级字符串解析 |
| Skill 验收（`0.9.2` 发布） | `src/core/skill-profiles.mjs` + `src/core/skill-validation.mjs` | 规则表是纯常量、判定是纯函数：只读 `SKILL.md` 文本与目录清单，**不调用模型**、不执行 Skill 里的脚本 |

任何未来新增的模型用途（包括反馈或远程分析）必须先定义接收方、用途、保存周期与单独授权。

**一个状态词必须能被界面上的内容证实——说不出「我怎么知道它做到了」的状态，不许显示。**

## 10. 技术约束与集成点

### 10.1 有效版本与既有事实

- 当前本机基线 DSH `0.1.1-rc.2`，仍处 RC API 演进阶段；
- 只依赖已验证的公开服务与事件契约，**不读取 DSH 私有内部状态**；
- Observer / Receipt Builder / Storage 必须可独立替换；
- UI 不直接解释原始 SessionEvent，统一读取业务对象；
- 两个一级页面各有唯一投影（本次 Skill 读收据 load evidence，已安装 Skill 读 `buildInstalledView`），**不得互相借用数据源**；
- Consumer 覆盖采用产品级验证矩阵；单条事件仍保持身份不可区分，未验证形态用 `coverage-unknown`。

### 10.2 宿主面

- 宿主路由 `0.8.0` 口径 **11 条**（`0.9.2` 发布口径 **12 条**，第 12 条是 §5.10 的 `POST /skill-trace/modify`；`1.0.0` 发布口径 **13 条**，第 13 条是 §5.13 的 `POST /skill-trace/evaluation`），全部在 `src/dsh/host/index.js`，由守卫按字面钉住：`GET /skill-trace/context`、`GET /skill-trace/definition`、`POST /skill-trace/translate`、`GET /skill-trace/catalog`、`GET /skill-trace/skills`、`GET /skill-trace/skill`、`POST /skill-trace/preferences`、`GET /skill-trace/translation`、`DELETE /skill-trace/translation`、`POST /skill-trace/clone`、`GET /skill-trace/diff`（V0.8 新增，§5.7）。
  **（以代码为准）** 归档 PRD 的 §12.1 / §16.6 与 `DEC-27` 写的是「7 条」，其中含 `/installed`；实测没有 `/installed`，多出 `/catalog`、`/translation`（GET + DELETE）、`/clone` 与 `/diff`；`0.9.2` 发布口径再加 `/modify`（§5.10，只记内存与代发消息，**不写文件**）。`0.8.0` 时守卫按字面匹配这 11 条，`0.9.2` 发布口径匹配 12 条，`1.0.0` 发布口径匹配 13 条，并反向钉住 15 条已删路由。§5.11 的排序**不在这张表里**：它只往 `GET /skill-trace/catalog` 的响应里加 `ordering` 与每个 Skill 的 `addedAt` / `lineage`，条数不变。
  **V0.9.0 的验收没有新增路由**（`0.9.2` 发布口径，§5.9）：`GET /skill-trace/skill` 与 `GET /skill-trace/definition` 两条响应各多一个同级字段 `validation`，宿主里由同一个 `validationFor()` 产出。
- 集成点：`ctx.skills.snapshot()`（读发现结果与完整性，作 `buildInstalledView` 输入）；`ctx.skills.get(name)`（用户进详情时按需读取当前定义）；`skills/change`（触发目录重新读取，不作为增删改明细）；`session/event`（观察 Session 事件）；`session/flush`（本地收据一致性收口）；`ctx.llm`（**唯一模型调用入口**，只在用户触发翻译时使用一次）；`ctx.sessionPersistence`（恢复 / 读取既有事件能力）。
- **宿主改了必须重启 DSH**：宿主把模块读进内存后不会自动换，不重启打接口得到的是旧答案，而且它答得很正常、不会报错。客户端半边硬刷新浏览器即可。
- **`dist/client.js` 是提交进仓库的发布产物**，不是构建缓存；守卫会报 `dist/client.js is stale or missing — run \`npm run build:client\` and commit the result`。

### 10.3 客户端预算与依赖收敛

- `dependencies` **必须保持为空**；`devDependencies` 只有 `esbuild`；可选 peer 只有 `@deepseek-ai/dsh-llm`（翻译用）；
- **新依赖、新路由、新页面的默认答案是「不加」**；画布类 `elkjs` / `@xyflow/react` / `mermaid` 由守卫直接拒绝——框架画的是角色与小节，不是图；
- 客户端只能 `require` 这几支 core 模块（构建时内联，**恰好七支**）：`flow-evidence.mjs` / `skill-framework.mjs` / `skill-runtime-logic.mjs` / `markdown-table.mjs` / `installed-view.mjs` / `translation-cache.mjs` / `skill-clone.mjs`。渲染烟测的降级器**只认** `export function` / `export const` / 单行具名 `import`——新的 core 模块要么无依赖，要么只用单行具名 import；
- **验收器不走这条缝**：`skill-profiles.mjs` / `skill-validation.mjs` 是宿主侧模块，客户端**不 `require`** 它们，验收结果只经 HTTP JSON 上界面（因此也不必进上面那张白名单）；
- **列表首屏不读 `SKILL.md` 全文**，进入详情才读；翻译只由用户点击触发；
- 定义正文**永不落盘**，只在活会话上现读现返；资源基的绝对路径只暴露类别、不暴露路径。

### 10.4 布局合同

```
Browser Viewport ≠ DSH Content Area ≠ Plugin Content Area
```

插件高度必须**测量宿主**：向上找最近一个有确定高度的祖先，取其底部到插件顶部的距离，发布为 `--st-host-h`；根规则读 `height: var(--st-host-h, 100%)`，**测量缺失时退化为 `100%` 而不是一个错误数字**。链条里**不许出现 `100vh` / `100dvh` / `calc(100dvh - Npx)`**，每一层必须同时具备 `height:100%`（或 `flex:1`）**与 `min-height:0`**——少了 `min-height:0`，flex 项不肯收缩，整条链会悄悄退回内容高度。

**布局契约是设计约束，不是实现细节**：根规则曾被一个多删的 `}` 关进 `@media(max-width:1050px)`，桌面宽度下整条根规则完全不生效（`font-size` 回退 16px，整个 UI 大一号；`height` 塌成内容高度），而**当时 337 项测试全部通过**——因为没有一条测试把样式表当 CSS 解析。现在由 `test/layout-contract.test.mjs` 守住：根规则必须在**花括号深度 0**、必须携带排版与布局基准、高度链禁止视口单位、花括号必须配平。

### 10.5 渲染合同与守卫

- `conversation.view` 是**没有错误边界**的 React slot：组件一抛错，**整个标签页空白**。同一个组件里，`React.use*` 不得排在第一个提前 `return` 之后（第一帧少调一个 hook、第二帧多调一个 → React #310 → 白屏）。两道守卫：`HOOK_ORDER_OK` 与 `test/client-hook-order.test.mjs`。
- **对象不能当 children**（V0.9.0 踩到）：双语标签是 `{zh, en}` 对象，`raw()` 只是打上「别翻译」的标记、**不做字符串化**；直接 `h('code', null, raw(label))` 会抛 React #31（Objects are not valid as a React child），同样整页白屏。必须显式选一种语言（`label?.zh`）再渲染，并回退到 id。守卫已按字面钉住这一条。
- 推论：**接口字段缺失必须降级成可见错误态**，不许在 `undefined` 上取属性；「读不到」与「没有」是两句话。
- `installStyles()` 是模板字符串：**CSS 里不许出现反引号**（包括 CSS 注释里的中文说明），否则 `node --check` 报 `SyntaxError: Unexpected identifier`。
- 颜色只能来自 `--st-*` token（`VISUAL_TOKENS_OK`）；字号带：页面标题 ≤18px、辅助文字 ≥10.5px、小节标题 14–16px、卡片标题 13–15px；圆角 / 分隔线比 ≤5.5 且分隔线 ≥3（结构靠分隔线，圆角是例外）；顶栏 48px、详情事实列 280px、文档目录 170px。

### 10.6 证据词表与只读边界

- 证据词表是封闭五值，唯一来源是 `src/core/flow-evidence.mjs` 的 `FLOW_EVIDENCE_FORBIDDEN` 与 `src/core/skill-runtime-logic.mjs` 的 `RUNTIME_LOGIC_FORBIDDEN`：

| 值 | 界面中文 |
|---|---|
| `runtime-supported` | 有相关运行证据 |
| `partial` | 部分相关证据 |
| `intent-supported` | 仅有模型意图 |
| `insufficient` | 暂无足够证据 |
| `unknown` | 无法判断 |

- **「暂无足够证据」不等于「没有执行」**。禁用词包含 已执行 / 未执行 / 已完成 / 未完成 / 执行成功 / 执行失败 / 已运行 / 未运行；运行逻辑那边另加 已加载 / 已读取 / 已注入 / 已生效。
- `attachEvidenceToFlow()` **只从 flow 取 `id/order/title/kind/line/evidenceType`**，其余全部放进 `evidence.*`——运行时只能标注，不能增删改序。
- **不读工具参数与结果内容**：`runtime-evidence.mjs` 是唯一接缝，守卫拒绝任何开始读 `args` / `result` 内容的改动。
- 「已安装」投影里只允许 `{name, description, provider, invocation}`——**不外发绝对路径**。
- 复刻写入**不用 `ctx.fs`**：它没有 `mkdir`，且 `writeText` 被围栏在 workspace 内，够不到用户级 Skill 目录。

### 12.3 真机验收清单（改完界面至少过一遍）

用**复杂 Skill**（`ui-craft`：342 行 / 11 小节 / 39 个引用），不要用四步的示例：

- [ ] 一级页面两个，点进同一个详情页，返回键写明是从哪个列表进来的；
- [ ] 已安装列表的卡片整张可点进详情，页面上没有多余的「查看详情」按钮；
- [ ] **Skill 框架**标题右侧是「N 个小节 · M 步声明流程」，不是「共 4 步」；
- [ ] 八个角色模块只显示**真的存在**的角色，缺的走一行「`SKILL.md` 里没有可识别的模块：验证 · Verification」；
- [ ] 「声明流程」在**框架内部**，是子模块，不是框架本身；
- [ ] 「渐进披露」显示「声明引用 N 个 · 已读取 **0** 个」，资源按 Tier 分层，每行带 `SKILL.md` 自己写的那句「什么时候读」；
- [ ] 「本次运行逻辑」五段，每段有状态与**真实事实**（Skill 数 / 载入位置 / 指纹）；
- [ ] 「步骤证据」每个声明步骤一行；没有证据的那几行只有一句「没有可展示的证据引用」，不会先立一个名头再由值把它收回；
- [ ] `SKILL.md` 在**最下面**；
- [ ] 界面里**任何位置**都没有「已执行 / 已完成 / 执行成功 / 已加载 / 已读取 references/…」；
- [ ] 文档里的表是**真表格**（带边框），不是一列竖线；
- [ ] 点框架小节 → 滚到 `SKILL.md` 对应章节并高亮；合成小节**不可点**；
- [ ] 中文阅读版：翻译后 `SKILL.md` 字节不变；退出 DSH 再打开同一 Skill，正文没变时译文还在；正文一变退回原文并允许重译；没写成本机时界面直说不说「已保存」；
- [ ] 复刻：对话框就地校验、同名 `409` 提示改名、成功态来自回读、目录刷新观察不到时写「待确认」、响应与界面都没有绝对路径；
- [ ] 顶栏：状态行只在有话要说时出现；「正在读取 / 读取失败 / 目录可能不完整 / 目录无法确认」四句一字不少；搜索框只在已安装列表出现；两个列表的元信息行都钉在卡片左下角，且两个列表从同一个位置开始。
- [ ] **Skill 验收**（`0.9.2` 发布，`FR-VAL-*`）：结论只在三态之间（通过 / 需要修正 / 无法判断）；**警告不为零时结论仍可以是「通过」**；每个 Profile 一行，`Microsoft` 的目录名规则在 `DSH` 下**不存在**（同一份 Skill 两种结论）；「这次没有判定」逐条列出**理由**而不是留白；点开「这次验收查了什么、没查什么」能看到限制；**没有**分数、等级、「优秀 / 最佳」；**没有**「已执行 / 已完成 / 已加载」；发现行同时给出 `rule id` **与**规则标题。
- [ ] **已安装列表排序**（`0.9.2` 发布，`FR-ORD-*`）：刚复刻出来的那个出现在**第一行**；卡片上有 `MM-DD 加入本机`（**只到日**，没有时:分），复刻过的多一行 `复刻自 <来源>`；默认成立的「模型可调用 / 可用 `/name` 调用」与 `filesystem` **一个字都不出现**，插件提供的 Skill 才写出它的 provider；列表上方那句话与真实顺序一致，读不到时间的 Skill 在末尾且被**报数**；界面里**没有**「今天 / 刚刚 / 几分钟前」；同一个 Skill 不重复出现。

### 12.4 已知的未验证项（不得声称已完成）

- **真实 DSH Desktop WebView 内的人眼走查**（亮色 / 暗色主题、1180 / 980 两个断点下的可读性）——渲染台截图**不能替代它**：渲染台自带视图选择、不加载宿主主题，且只截最后一帧，看不到需要两帧才出现的错误。清单见 `docs/RELEASE.md` §7.2；
- **系统级无障碍审计**；
- **Dark Mode 不得声称「已适配」**：机制已实现（14 个 `--st-*` token 映射 + `color-scheme: light dark`），但尚未在真实 DSH Desktop 上验证 Light / Dark 的实际观感，也没有 Dark 截图；
